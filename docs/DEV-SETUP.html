02 — Clone & install

Two repos, side by side

pyproject.toml declares AgentTwin — the world simulator the demo server and the test suite both build the fake shop from — as a local editable path, ../agenttwin. It has to sit next to this checkout, not inside it.

git clone git@github.com:dataagentsai/reference-agent.git
git clone git@github.com:dataagentsai/agenttwin.git
# now: .../reference-agent  and  .../agenttwin, as siblings

cd reference-agent
uv sync --extra dev

The import contract in pyproject.toml forbids support_agent from ever importing agenttwin — "a system that can see its own simulator is a system whose results mean nothing" — so this dependency is dev/test-only, never a runtime one.

03 — Running it

Three levels, each one exit further

Each level swaps exactly one thing out for the real version — the model, then the store — so you can tell which part you're actually testing.

Level 1 — scripted model, no Docker, free

No credentials, no containers, no network call. The simulated shop is projected in-process from worlds/clothing.yaml; the model is a canned script.

uv run python scripts/run_server.py

Open the printed URL — it carries a token the local test issuer minted for you, plus a separate desk link (/ops/desk) for approvals and escalations.

Level 2 — the real model, via Groq needs GROQ_API_KEY

Brings up Postgres, the LiteLLM gateway and Keycloak; the agent now calls a real model through the gateway rather than the script.

cp .env.example .env
# edit .env — set GROQ_API_KEY=<your key>, see §04
docker compose up -d
uv run python scripts/run_server.py --real

Level 3 — + the real store

Adds Saleor, a real e-commerce backend, behind its own MCP server — every tool call is now checked by a far end rather than trusted.

docker compose --profile store up -d
uv run python scripts/run_server.py --real --store
04 — Keys & secrets

What you actually have to supply

Everything in .env.example ships with a working local-dev-only default. There is exactly one secret you have to bring yourself.

VariableRequired?Where it comes from
GROQ_API_KEYyes Free key from console.groq.com. Set it in .env before docker compose up -d. Only the litellm container ever reads it — the agent itself never holds the provider credential, by design (AHC-0004).
AGENT_GATEWAY_KEYno The agent's own scoped key to the LiteLLM gateway — rate-limited (30 rpm) and budget-capped ($5) by default. Auto-created by the one-shot litellm-keys service on first up; the local-dev-only value in .env.example just has to match on both sides.
everything elseno DB passwords, the LiteLLM master key, Keycloak admin password, Langfuse keys, Chatwoot secrets — all default to local-dev-only placeholders that work as-is for local dev. Change them only if you're exposing a profile beyond your own machine.
Nothing to copy if you skip Level 2/3

A fresh clone with no .env at all runs fine at Level 1 — the local issuer signs its own tokens and the scripted model needs no key.

05 — Docker Compose profiles

One file, opt-in pieces

The whole stack doesn't fit in the ~4 GB Docker gets on an 8 GB laptop, so everything past the default set sits behind a profile. Add one at a time unless your machine has the memory for all of them together.

CommandAddsPorts
docker compose up -dPostgres, the LiteLLM gateway, Keycloak — the default set every level above needs5433, 4000, 8080

06 — Testing

One command, three build checks included

uv run pytest

Runs the whole suite plus three build-time checks that cannot be skipped: strict mypy, the import-linter architecture contract (5 rules — e.g. only llm may import a provider SDK, only tools may speak MCP), and ruff size/complexity ceilings. Database-backed tests skip cleanly if no Postgres is reachable, rather than failing.

07 — Gotchas

Things that bite on a first run

Linux Docker / a Codespace needs --host 0.0.0.0

Chatwoot's containers reach the agent over host.docker.internal. Docker Desktop (Mac/Windows) maps that to the host's loopback automatically; plain Linux Docker does not, so the agent has to listen beyond 127.0.0.1 there: uv run python scripts/run_server.py --host 0.0.0.0.

Changing deploy/keycloak needs a dropped database

The support realm is imported once, on first start. Keycloak never overwrites an existing realm, so editing that file and re-running up does nothing until you drop the keycloak database (or the whole postgres_data volume).

Seeding Saleor

After --profile store up -d, python deploy/saleor/seed.py populates the orders the scenarios and shadow tests expect. The admin login it creates is SALEOR_ADMIN_EMAIL / SALEOR_ADMIN_PASSWORD (both default to local-dev-only values in compose.yaml).
