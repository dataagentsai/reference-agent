Three messages, step by step

A question it answers alone

“where is AB-10001?”
  1. Keycloak's token is verified; the customer id comes from it, never from the text.
  2. The router sees an order-status question and takes the direct route: no model call.
  3. One read, get_order, to the store server, which checks the token and that AB-10001 is this customer's.
  4. Saleor answers fulfilled; the server says shipped — Saleor records dispatch, not arrival.
  5. “Order AB-10001 is currently shipped.” Cost: one read, no tokens.

An action it confirms first

“I don't need AB-10002 anymore” · “yes”
  1. The model proposes cancel_order. The customer never said cancel, so the policy refuses the call and the agent asks.
  2. The customer says “yes”: that turns the pending question into consent for exactly this order.
  3. The call runs, with an idempotency key the store remembers.
  4. The store checks the order is still pending, and cancels it in Saleor.
  5. The reply says cancelled only because the store's result says so.

A refund that needs a person

“refund AB-10003 please”
  1. The agent asks Temporal for an approval. The workflow reads the order's total itself, and it is over the limit.
  2. The customer is told a colleague will authorise it, and that nothing is refunded yet.
  3. A colleague grants it, or the 24-hour timer expires. The customer can leave; the wait survives restarts.
  4. On a grant, the workflow's worker — its own Keycloak login, no refund scope of its own — calls the store, naming the approval. The store checks the approval, then grants the refund against the order's payment.
  5. Next time the customer writes, the agent reads the approval and says what became of it.

Postgres

Remembers that something is waiting. Everything that should happen — the expiry, the refund when granted, the retry — is code you write, schedule and keep correct.

A job queue

Runs work later, with retries. It does not know an approval exists between jobs, so "who decided, and is it still valid" lives somewhere else.

LangGraph interrupt

Pauses the agent's graph and resumes it later with a human's answer. Natural inside LangGraph; it has no timers and acts in the agent's own process.

Temporal

Runs the wait itself: it holds the state, fires the deadline, wakes on the decision, retries the effect, in a process of its own. We keep only the rules. The cost is one more server to run.

That is why the Open Stack uses Temporal and keeps conversations in Postgres. The LangGraph cycle (T-036) will test whether an interrupt can do the same job there; Postgres-native engines (DBOS, Hatchet) are the lighter option worth evaluating.

MCP, explained like you're five

The picture

The agent is someone who cannot cook. The store is a kitchen. MCP is the menu and the order ticket that every waiter and every kitchen agree on, so any agent can order from any kitchen without learning its language first.

What happens
  1. Read the menu — tools/list. The kitchen says what it can make and what each dish needs.
  2. Write a ticket — tools/call with a dish and its details, e.g. cancel_order {id: AB-10002}.
  3. Clip your ID to the ticket — _meta. The kitchen checks it itself and ignores what you say you are.
  4. Get the plate and a receipt — the result, as text and as structured data the agent can check.

Two kinds of “no”, and MCP keeps them apart: the kitchen tried and could not (an execution error — “that order has shipped”), or the ticket never reached a kitchen that understood it (a protocol error — no such dish). The agent treats them differently: the first it can explain to the customer, the second is a fault.

One tool call, on the wire

The model chooses which tool and writes its arguments. Everything that decides whether it is allowed — the token, the approval, the idempotency key — travels in _meta, which the model never sees or writes.

Today, and after T-054

The code already behaves as if the two were apart: the store verifies a token addressed to itself and trusts nothing the caller asserts. T-054 makes the process boundary real.

Are we using FastMCP?

Yes — the one in the official SDK

FastMCP 1.0 was merged into the official MCP Python SDK, and in SDK 2.x (we run mcp 2.1.1) it was renamed MCPServer. That is what order_system/server.py and AgentTwin's projection build on: the @server.tool decorator, schemas from type hints, Context for _meta. Importing mcp.server.fastmcp in this SDK raises an error pointing at the rename.

No — the separate fastmcp package

The standalone FastMCP 2.x project adds server composition, proxies, servers generated from OpenAPI, auth providers and a richer client. We need none of that yet: one server, six hand-written tools, one client. The official SDK is one dependency, versioned with the specification, and our import contract keeps MCP inside one module, so moving later is a small change. Worth another look at T-054 if its auth helpers save writing the connection's OAuth.

Is what we send to OpenTelemetry enough?

What is sent

35 span types, each held to a contract (telemetry/contract.py): the route and why, each tool with its side effect and idempotency key, the escalation rule and outcome, approvals, tokens, model, cost per call and per run, why a run ended, context size, unbacked promises, breaker and retries, and user.id / session.id on the root so Langfuse groups by conversation.

And seven counters with bounded labels (telemetry/counters.py): turns, escalations, refusals, approvals, unbacked promises, spend, model calls.

What is missing
  1. The counters go nowhere. No MeterProvider is configured, so all seven record into a no-op.
  2. The approvals counter counts only requested since the move to Temporal.
  3. No latency histogram: turn, model call, time to first token, each tool.
  4. No words are ever captured. set_payload is off by default and called from nowhere, so switching it on changes nothing. A judge has nothing to read.
  5. Tool arguments and results are not on the tool span.
  6. Nothing writes a score back to Langfuse.
  7. Nothing joins what happened later to the run: the customer came back, a refund was reversed.
  8. The trace stops at the MCP hop (T-020).

Enough to investigate one run. Not enough to notice that many runs have gone wrong.

Why Prometheus and Grafana beside OpenTelemetry and Langfuse

OpenTelemetry is a format and a way to ship data, not a place to keep it. A trace is everything about one request — large, often sampled, slow to count across thousands. A metric is a number already counted — tiny, kept for months, and checked against alert rules every few seconds. Langfuse is built to read and score traces; Prometheus is built to hold numbers and alert on them; Grafana puts every source on one screen, including Temporal, Postgres and Keycloak, which already publish Prometheus metrics. An exemplar joins the two: a spike on a chart links to one trace that was in it.

None of the right-hand side is in compose.yaml yet. T-055 adds the Collector, Prometheus, Grafana and Alertmanager.
