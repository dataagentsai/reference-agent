Start hereWhat it actually is

A customer writes: "please cancel my order AB-10002". Something has to read that, work out what they want, check whether it is allowed, and either do it or explain why not.

That is the support agent. It is a piece of software with an AI model inside it — and the model is one part, not the whole thing.

The model decides what to try. The rules decide what happens. If you remember one sentence from this page, that is the one.

The rulesFour things it can do

These are not in the agent's code. They are in one text file the agent reads at run time — so a shop with a 14-day window needs no code change.

Cannot be undone

Cancel the order

Only while pending or confirmed. Once the warehouse has picked it, too late.

Can be undone

Only if delivered, and 30 days or fewer, and not final sale. All three.

Can be undone

Only while still pending. After that the carrier has it.

Needs a permission the agent does not normally hold. Above ₹10,000 a person approves first.

Nothing below is hard-coded. The answers are worked out from the same four rules.

A refusal is a normal answer, not an error. Getting a no right matters as much as getting a yes right — a wrongly-allowed return costs money, a wrongly-refused one costs a customer.

The doorWho calls it, and how the values are made

Everything below is a real request, really made, with the real values it produced. Nothing invented.

Until today nothing called the agent at all. Every caller was a test or the simulator, so the entry point had a door and nothing on the other side of it. There is now a web server, and writing it forced a fix that had been sitting on the list as an abstract problem for days.

Here is the whole path, from what the browser sends to the four values the agent is handed.

What arrives on the wire

The customer typed a sentence and pressed Enter. This is what the browser actually sent.

POST /chat HTTP/1.1 authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6… idempotency-key: msg-a1b2 content-type: application/json {"text": "hi, where is my order AB-10003?", "conversation_id": null}

Four things, and each becomes one argument. Only the first is anything the customer chose.

1

text — straight from the body

The only argument the customer supplies directly, and the only one they are permitted to. Rejected if it is missing, empty, or not a string.

the code
text = body.get("text")
if not isinstance(text, str) or not text.strip():
    raise BadRequest(400, "text is required")
the value it produces
"hi, where is my order AB-10003?"
2

identity — from the signed token, never from the body

The header is Bearer <token>. The token is a signed blob the customer cannot forge and cannot edit — change one character and the signature stops matching.

the code
header = request.headers.get("authorization", "")
token  = header[7:].strip() if header[:7].lower() == "bearer " else ""
who    = ident.verify(token, secret=secret)   # signature + expiry
what is inside the token
{
  "sub": "C-1042",              ← who
  "scp": ["orders:read",        ← what they may do
          "orders:write",
          "returns:write"],
  "iss": "support-agent",
  "iat": 1788594919,            ← issued
  "exp": 1788598519             ← expires, 1 hour later
}
the value it produces
Identity(
    customer_id = "C-1042",
    scopes = frozenset({"orders:read", "orders:write", "returns:write"}),
)

Look at what is not in that list: refunds:write. That single absence is why the refund tool never appears in the list of tools the AI is shown. Not refused — invisible.

And this is the line the whole security model rests on. If customer_id were read from the JSON body, every customer could type "customer_id": "C-9999" and become somebody else. There is a test that sends exactly that alongside a valid C-1042 token and asserts the body's claim was ignored.

3

delivery_id — a header the caller controls

The browser generates one per message, not per attempt. If the network drops and it retries, it deliberately sends the same id — which is what makes pressing send twice safe rather than a second cancellation.

the code
delivery_id = request.headers.get("idempotency-key")
the value it produces
"msg-a1b2"

If the header is absent the value is None and the turn runs unguarded. That is stated rather than defaulted: inventing an id here would give us a duplicate check that can never fire, and a green result to go with it.

4

conversation — loaded by the id the customer holds

On the first message there is no id, so there is nothing to load and the value is None. The agent creates a new conversation and returns its id in the reply.

the code

This is the line that could not be written until this morning. State was filed under run id, a fresh one is minted every turn, and no customer has ever held one — so there was no way to turn what a customer presents into state. It had been on the list for days as an abstract memory problem. It is not abstract: it is the fourth line of the handler.

Someone else's conversation id returns not found rather than forbidden. Confirming it exists would tell an attacker their guess was right.

The frameworkStarlette now, FastAPI when it pays

There is no FastAPI in this repository. Whether there should be is a fair question, and the answer is yes, later, and for one specific reason.

The door you just read is hand-wired. serve/__init__.py is 269 lines, imports Starlette directly, and declares three routes:

routes = [Route("/", page), Route("/healthz", health), Route("/chat", chat, methods=["POST"])]

The project description says it out loud — "built to the AI Harness Catalog's sixteen layers, with no framework." That is a deliberate choice, not an oversight.

FastAPI is Starlette. It is a layer on top of the same routing, the same requests, the same responses. So "moving to FastAPI" is not a rewrite of the server — it is adopting four conveniences on top of the one you already run.

What the four conveniences are worth here

Today, with one real endpoint, the honest answer in three of four rows is "nothing".

What FastAPI addsWorth todayWhy
Pydantic request models small Replaces ~10 lines of isinstance checks in decode. The contracts already exist in contracts/; this would be a second declaration of shapes Pydantic already owns.
Dependency injection small One endpoint needs identity. One. DI pays when several routes need different scopes.
Automatic OpenAPI docs none Nobody is integrating against a browser page and one chat endpoint.
Declarative status codes none This agent returns five different statuses from one route, chosen by result type. That stays an explicit map either way.

Mechanically that is an afternoon. The cost is not the code — it is the error contract, and this repository has tests that pin it.

400 → 422

Six tests assert 400 that FastAPI would answer 422

Missing text, empty text, whitespace only, text is not a string, body is not an object, conversation id is not a string. Preserving 400 means a custom RequestValidationError handler — which claws back most of the "less code" win.

Leakage

FastAPI's default errors describe the schema

The 401 path is deliberately opaque. Its comment: "the library's own text is descriptive — every word of that tells whoever is probing which part of the token they got wrong." A test asserts the body is exactly {"error": "the session token is not valid"}. Verbose validation errors are the same leak in a different place.

Seam

decode is deliberately one testable unit

"Either an Inbound exists or the request was refused." DI spreads that decision across dependencies, so the answer can be half-made. Recoverable, but it is a real property being traded away.

Free

Lifespan and the 413 guard port unchanged

FastAPI takes the same lifespan= context manager, so the MCP-connection-opened-in-the-serving-task fix survives as written. The size cap stays middleware, refusing before parsing.

Verdict

Do it with the reviewer surface, not before

Converting one endpoint buys documentation nobody reads and puts a pinned error contract at risk. Converting six buys scoped dependency injection, a real integration surface, and request shapes worth declaring — by which point you will also know what those shapes are. Until then Starlette is not technical debt; it is the smaller thing that fits.

Its memorySix kinds of state, and they are not the same kind

"Memory" is one word for several different things here. Mixing them up is how a system ends up unable to answer the question it was built to answer.

The conversationsurvives a restart

What was said, in order, plus whether an approval is outstanding. Filed under both the run and the conversation — the run index explains a past turn, the conversation index is the only one a customer can reach, because a customer holds a conversation id and never a run id.

What has been donesurvives a restart

Every numbered action that changed something, and what it returned. Asked before anything runs: have we already done this exact one? This is what makes a retry safe rather than a second charge.

Pending approvalssurvives a restart

What was asked, by whom, when it expires, who decided and which way. It also carries the original action number — which is why approving twice still refunds once.

Handled messagesin memory only

Which deliveries have already been processed. Honest about its limit: it answers "did this message arrive twice" for one process and not for a deployment. And the durable version is a superset, not a swap — settling runs in a finally, which a killed process skips, so a durable claim outlives its writer and needs an expiry this one does not.

Recordingsfiles on disk

What the model actually said, captured once and replayed forever. Not runtime memory — this is what makes a test suite free and repeatable. Each recording carries the configuration it was made under and refuses to replay under a different one.

The tracecurrently kept nowhere

17 declared kinds of event — every model call, tool call, routing decision, policy check, approval and HTTP request. Enough to reconstruct a whole job afterwards. And it is currently sent nowhere, which is on the list below.

None of this is the shop's data. Orders live in the shop; all six of the above belong to the agent. That separation is deliberate and load-bearing: the shop is the thing a simulation replaces, and the agent's own records are what the tests read to decide whether it behaved. A record that could be faked would not be worth reading.

And what is deliberately absent: there is no long-term memory of a customer across conversations, no stored preferences, no vector store, nothing learned. The text sent to the model is assembled fresh each turn from the stored conversation and trimmed to fit. An agent that remembered more would need a much longer answer to "what does it know about me", and this one can answer it exactly.

Why the ledger cannot do the delivery log's job

This is the question worth sitting with, because the answer is not obvious and the code exists precisely because someone got it wrong first.

The ledger keys on run:step:iteration. A duplicate delivery does not repeat a step inside a run — it starts a whole second run, with its own fresh run id. The two runs therefore never share a key space, and the ledger cannot see across them. It is looking at the wrong axis entirely.

That is turn 4 in the trace above. It stops at deliveries.claim, three calls in. Had it not, the second run would have minted new keys for every action, found nothing in the ledger, and cancelled the order a second time — correctly, each time. Nothing inside either run would have been wrong, which is why nothing inside a run can catch it. The defence has to sit one layer above where the duplicate happens.

The PRIMARY KEY on the ledger is not decoration — it is the entire mechanism. The ledger is correct because the database refuses a second row for that key, not because the application remembered to look first. Two processes racing on a retry both lose, which is the only outcome worth having.

Two schemas, and the split is load-bearing

agent_state is everything above — the agent's own records. ecom is the business world: customers, orders, shipments, refunds. The line between them is what makes the tests mean anything.

agent_state is the oracle — what the assertions read to decide whether the agent behaved. The simulator never projects it, because an oracle that can be faked is not one. ecom is the half a simulation replaces, and in a simulated run the agent reaches it only through a projection server that never touches the real schema.

They are separate schemas rather than separate tables in one so the boundary can be enforced by a grant rather than by remembering. A role that can read ecom and write agent_state cannot accidentally do the reverse.

And one line in ecom is part of the agent's safety, not the shop's bookkeeping:

The ledger prevents the second call. That UNIQUE makes the second row impossible even if the call is somehow made — the control repeated at the destination, where it does not depend on us being right. Note its limit, though: it dedupes a key, so it stops a retry. It does not stop two independent runs, which carry two different keys. That matters below.

Coming back after the laptop hangs

A customer's browser dies mid-conversation. They reopen it an hour later and say "let's resume". That works, and it is the fix filed as F-006 — before the store could be read by conversation id, the handler could not even be written.

The next message arrives carrying its conversation_id. The server reads store.latest(conversation_id) — newest checkpoint for that conversation, which is what the (conversation_id, updated_at DESC) index is for — decodes it, and checks that its customer_id matches the token's. A mismatch returns 404, not 403: confirming the conversation exists would tell someone their guessed id was right. Then the turn runs with all prior messages in place.

If an approval was outstanding, pending_approval_id in that checkpoint sends the turn to _resume before anything else — turns 6 and 7 in the trace. Nothing was blocked or held open in the meantime; the approval returns, it does not wait.

What it needs: the client must still have the conversation id. There is no lookup by customer — no "list my conversations" — so a genuinely fresh browser with cleared storage starts a new conversation rather than finding the old one. The id is the only handle, by design, and that design has this cost.

Two browsers, two messages, one customer

Now the harder version. The same customer has two tabs open. In one they type "cancel this order"; in the other, "cancel my latest order". Both are in flight at once. This is not handled, and it is worth being exact about why.

Two different conversation ids

Both deliveries carry different message ids, so both are claimed. Two runs, two key spaces — the ledger sees nothing in common. Both reach cancel_order.

What stops the second is not the agent. It is the shop: the order is already cancelled, and the rule needs pending or confirmed, so the second call is refused on its precondition. Safe — but by the world's state machine, not by anything here.

The same conversation id

Both read latest() and get the same prior state — neither sees the other's message. Both run. Both write a checkpoint, under different run ids but the same conversation.

latest() then takes whichever has the newer updated_at. The other turn's messages are gone from the history — though its effects already happened. A lost update, undetected and unreported.

And the example is sharper than a duplicate, which is what makes it interesting. "cancel this order" and "cancel my latest order" may not even resolve to the same order — the second is evaluated against a world the first may have just changed. So this is two different intents racing on stale reads, not one message arriving twice. No deduplication mechanism is the right shape for it: there is nothing to deduplicate.

What is missing is a claim at the conversation level — the delivery log's exact shape, keyed on the conversation instead of the message — or a version column on checkpoints with a conditional update, so the losing writer is told to re-read and retry rather than silently overwriting. Neither exists today. There is no FOR UPDATE, no advisory lock and no version anywhere in the state layer; the write is a plain upsert on run_id and the read is ORDER BY updated_at DESC LIMIT 1.

The trigger module's own docstring claims it answers "two turns for one conversation in flight at once". That claim is broader than the code. The guard keys on the delivery id, so it catches the same message twice and not two different messages on one conversation. It is on the list below.

"Show me all four items, cancel one, keep three"

A reasonable sentence, and the system cannot represent it. This is the most instructive gap on the page, because nothing in it is a bug — every component does exactly what it was built to do.

An order here has six fields: id, customer, status, days since delivery, whether it was final sale, and a free-text note. It has no items. There is no line, no quantity, no SKU, and no table for them in either schema. So the first half of the request has no data to answer it with — get_order can return a status, and there is nothing else to show.

The second half is worse, because it looks answerable. cancel_order takes an order id and sets status: cancelled. Whole order, atomic. There is no item id to pass and no field in the schema that would carry one — so the closest thing to "cancel one of four" that the agent can actually do is cancel all four.

Now walk it through the guardrails, and watch every one of them pass:

Permissionpasses

The customer holds orders:write. Cancelling their own order is exactly what that scope is for.

Schemapasses

{"id": "AB-10002"} validates against the tool's input schema. It is a well-formed call in every respect.

The shop's rulepasses

allowed_when: status in [pending, confirmed]. The order qualifies, so the world applies the change and reports success.

The reply checkpasses — and this is the problem

"I have cancelled that order for you" is screened against what actually happened, and it is true. The order was cancelled. The sentence is accurate and the outcome is wrong.

That last one is the point worth taking away. The truthfulness check asks did this happen, and the permission checks ask was this allowed. Nothing anywhere asks whether it was what the customer meant. A correct, permitted, truthfully-reported action that destroys three items the customer wanted is invisible to every control in the system, because none of them holds a representation of the request to compare against.

And the fix is not a better prompt. Telling the model to be careful about partial cancellations does not create an item to cancel. The fix is in the ontology: an order_item entity in worlds/clothing.yaml, and a tool scoped to one — at which point the generated schema carries an item id, the simulated server enforces it, and "cancel one of four" becomes a request the system can both express and refuse correctly. The world file is the data model, so this is one edit in one place rather than a change to the agent.

Until that exists, the honest behaviour is refusal, and the safest place to put it is the router — refuse patterns run before intent, so a request naming individual items can be turned away before the model is ever asked to find a tool for it.

The cataloguesHow AHC and AAC show up in this code

A hosted platform hosts itself. If somebody else runs the loop, they run the machine. That is the offer.

A cloud's model plane pulls its everything-else. Not forced — you can call Bedrock from anywhere — but the reason to choose it is usually that the identity, billing and compliance story is already there, and taking half the bundle wastes most of the benefit.

Own loop · OpenAI-shaped surface · hosted open-weight models · runs anywhere.

Q1

When a customer clicks “Talk to our AI agent” and the box opens, does anything happen?

No — the box opens empty

There is exactly one route that does anything, POST /chat, and it requires text. So a session opening is not something the system can currently express at all — it is an entry point that is not a message.

What products normally do at that moment

Greet you by name. Show your recent orders so you can click one instead of typing a number. Surface anything already in flight — a return being processed, a refund waiting on a colleague. Offer to pick up where a recent conversation left off.

Why the absence costs something

The customer has to know their order number. Every scenario in our test suite opens with somebody who conveniently types AB-10003. Real people do not have it to hand — so the first two turns of a real conversation get spent working out which order, and those turns cost money. A list of three orders skips both.

Work already in flight is invisible. The agent knows there is a refund waiting on a colleague — it is recorded against the conversation — and the customer sees nothing until they think to ask.

It is the cheapest turn available and we are not taking it. Listing your own orders is a database read. Greeting you is a string.

And the design decision underneath it

Opening a chat must cost zero AI calls. The router already exists to stop questions with deterministic answers reaching the model, and “what are my orders” is the most deterministic question there is. A product that generates its greeting with a model pays for every abandoned open — and most opens are abandoned.

It also creates a new place for the failures we already know about. Showing someone else's orders is the identity check people skip on a read-only route. A greeting that says “your refund has been processed” when it has not is the same untrue-claim failure the truth oracle exists for — arriving now before the customer has typed anything. And orders listed at open and acted on a minute later is the same stale-read window we already simulate, moved somewhere nothing tests.

The simulator has the same hole

A scenario begins with an actor saying something. There is no way to write “the customer opened the chat and saw these three orders”, so the state a real conversation actually starts from cannot be simulated. Both sides need the same thing.

Q2

Who maintains the login and its permissions, and which open source would we use?

Nothing does — and answering it uncovered a critical defect

There is no login. A script signs a token and hands it over. No user list, no password, no way to revoke one, and no way to give one customer something another does not have — the permission list is a constant in the source code.

Asking the question found something worse than the gap

Before choosing any tool, it is worth checking what the permissions we do have actually protect. So: a different customer, a valid token, ordinary permissions.

# AB-10002 belongs to C-1042. This is C-9999. C-9999 called cancel_order on C-1042's order -> {'allowed': True} order status now: cancelled

A stranger cancelled somebody else's order. Nothing was forged, nothing was escalated, no guardrail was bypassed. Every one of the nine kinds of guardrail on this page did exactly what it was written to do.

Why all of them passed

Because none of them was ever asked this question. Look at the two sentences side by side:

what the permission says
orders:write   →   this caller may write orders
what the business means
              →   this caller may write their own orders

The first is a permission about a verb. The second is about a row — and a list of permissions has no way to say it. This is the most common serious flaw in web APIs, and here it had been sitting underneath nine layers of correct guardrails the whole time.

Why the tests never noticed

Every test, every scenario and every generated case uses one customer. C-1042 is in the fixtures, the shop seeds one customer, and the simulated customer is always that one. A fault that takes two customers to observe cannot be observed by a suite that has never had two.

The shop's description even states the relationship — every order records which customer it belongs to — and nothing reads it at the moment an action runs. A declaration that nothing consumes is decoration, which is a mistake this project has now made twice.

So: which open source?

Two different problems that get confused, and they want different answers.

Running a login and issuing tokens. Keycloak is the institutional answer — heavyweight, its own database, an admin screen that already does everything. Zitadel if you want something modern and multi-tenant from the start. Authentik for a friendlier admin. Ory if you want pieces rather than a product and are willing to assemble them.

Any of them also fixes a second problem quietly: our token is signed with a shared secret, so anything that can check a token can also create one. A real provider signs with a private key and hands out only the public one, so a compromised agent can read tokens and cannot write them.

Fine-grained permissions. OpenFGA or SpiceDB for “who is related to what” rules, Cedar or OPA for policy as code, Casbin to keep it in-process.

And the recommendation is to not use any of them for this

The fix for the defect above is a comparison, not an architecture. The place where a tool runs already holds both the caller and the row it is about to change; it just never compares them. Adding a permissions service to answer “is this yours” would put a network call in front of a field comparison.

Those services earn their place when the rule stops being “it is yours” — household accounts, a partner acting for a customer, an assistant acting for a partner. Not before.

The design, in one table

The reason this needs designing rather than shopping is that three different questions all get called “auth”, they are answered in three different places, and the one we got wrong is the one no product answers for you.

What is already right, and should not be touched

The middle row is genuinely well built. And the permission to actually pay exists nowhere except inside an identity minted from a live approval: it can be borrowed for one action and never held.

Where the fix belongs

In the shop's description, not the agent's code. The relationship is already written down — every order records which customer it belongs to — and nothing reads it when an action runs. So the shop gains one line per thing it owns:

Declared rather than coded, so a shop where orders belong to an account instead of a customer needs no code change — the same reason a fourteen-day return window is a file edit.

The system knows one kind of person: a customer. A real deployment has at least four — a customer, support staff acting on behalf of a customer, an approver, and the agent itself as a thing the shop's log can name.

Staff is the one that breaks a naive fix. They do not own the order and must still be allowed. That is delegation, and it is exactly the point where a permissions service starts to pay for itself: the rule stops being “it is yours” and becomes a relationship. Designing for it now costs nothing, as long as the rule is declared rather than written as an if.

Q3

What is the difference between a delivery id and an idempotency key, and how does once stop something happening twice?

Two different things, at two different doors

They sound alike and they are not the same. One names a message arriving. The other names an action about to run. They guard different doors, and neither can do the other's job.

Delivery idIdempotency key
Namesone message arriving from outsideone action inside one piece of work
Looks likemsg-a1b2run_7f2a:0:1
Made bythe browser, or the queue that delivered itthe agent itself, before the action runs
Checkedat the very front, before any work startsjust before a tool that changes something
Stopsthe same message being handled twicethe same action running twice inside one job

Why you need both — and this is the whole point

The idempotency key is built out of the run: run + step + position. And a second delivery starts a whole new run, with a new run id.

# first delivery run_7f2a → key run_7f2a:0:1 cancel AB-10002 ✓ done, recorded # the same message arrives again — a new run run_9c4b → key run_9c4b:0:1 cancel AB-10002 ↑ the ledger looks this up, finds nothing, and lets it through

The two keys share nothing. The ledger is working perfectly and has no way to know these are the same message — it cannot see above itself. That is why the delivery guard has to sit in front: it is the only place that can tell two runs came from one message.

How once actually works

It keeps a list of message ids, and each one is in one of two states: running or finished.

a message arrives with id msg-a1b2 1. look it up in the list 2. not there → write "running", do the work 3. there, finished → stop. "already handled" 4. there, running → stop. "still in progress" 5. work ends → write "finished"

That is the entire mechanism. Three details make it actually work.

1 · Looking and writing must be one uninterruptible step

If two copies of the message arrive at the same instant and both look before either writes, both see nothing and both proceed. So the look and the write happen inside a lock — nothing can slip between them.

the code
async with self._lock:
    existing = self._seen.get(delivery_id)
    if existing is State.SETTLED:   raise DuplicateDelivery(...)
    if existing is State.IN_FLIGHT: raise OverlappingRun(...)
    self._seen[delivery_id] = State.IN_FLIGHT

2 · “Finished” is written even when the work crashed

It is in a finally, so it happens whatever the outcome. A message that arrived and failed halfway has still arrived. Running it again would repeat whatever it managed to do before it died — which, for a cancellation, is the whole problem.

3 · Two different refusals, on purpose

“Already finished” and “still running” are different situations. A message arriving twice is routine — queues retry on purpose, and telling the caller off for it would make every well-behaved queue look broken. Two copies running simultaneously is a race, and somebody should look at it.

What this buys the customer

The browser generates one id per message, not per attempt. So when the connection drops and it retries, it deliberately sends the same id. That is what makes pressing Send twice on a bad train connection safe: the second one is recognised and answered, not obeyed.

And the honest limit

The list of seen messages is held in memory. One copy of the agent knows; a second copy running alongside it would not, and a duplicate could slip between them. The shape is already right — the durable version is the same two operations against a table — but today it protects one process, not a deployment.

Q4

Why are we building any of this? Won't a load balancer, gateway or queue handle it — and doesn't reading before writing solve it anyway?

Mostly we should adopt, not build — and one of those three makes it worse

This is not an agent problem. It is an ordinary distributed-systems problem — two copies of a program, one message, both check, both see nothing, both proceed — and it has ordinary answers that are better than ours.

What the usual infrastructure actually does

Does it solve it?
Load balancerNo — it is the cause. It is what puts two copies of the agent behind one address, which is precisely why an in-memory list stops working. It has no idea what a duplicate is.
API gatewayLess than people expect, and it may make it worse. Gateways do authentication, rate limiting and routing. Response caching accidentally deduplicates reads and does nothing for writes. And a gateway that retries on a timeout is a duplicate generator — a large share of real-world duplicates are manufactured by the infrastructure added for reliability.
QueueYes, genuinely. SQS FIFO, Azure Service Bus, Pub/Sub and Kafka all deduplicate as a configuration setting. Zero code.

But the queue's catch is the one nobody mentions. It deduplicates its own deliveries, inside its own time window, and only when the sender attaches a stable id per message. So the id is still the thing that matters — the queue is merely somewhere convenient to check it. Whoever mints the id owns the correctness. Our browser mints one per message rather than per attempt, and that is the part that is already right.

Does reading before writing solve it?

Partly — and it is the reason our own duplicate did no damage. Cancelling re-reads the order, finds it already cancelled, and refuses. The shop stopped it, not the agent. A protection that works by accident of the business rules is worth naming as an accident.

Three things it does not do.

It is not atomic. Read, then decide, then write is the classic race: two copies can both read pending, both conclude “allowed”, and both write. The window is small, not zero — and it is exactly what we already simulate deliberately.

It only works when the action destroys its own precondition. A cancelled order cannot be cancelled again. But sending an email, charging a card or calling a webhook have no state to re-read, and for those it offers nothing at all.

It protects the effect, not the conversation. The second attempt refuses correctly and the customer can still be told something contradictory. The data is safe; the reply is not.

So what is the clean answer?

1 · Make the action harmless to repeat, where the data lives. The best option by a distance, because it removes the coordination problem instead of solving it:

UPDATE orders SET status = 'cancelled' WHERE id = %s AND status IN ('pending','confirmed'); -- 1 row changed = we did it. 0 rows = somebody already had.

One statement. The check and the act are the same act, so there is no gap to race in. No lock, no lease, no claim list, nothing that can get stuck. A duplicate becomes harmless rather than prevented — and harmless survives crashes that prevention does not.

2 · Let the queue do it, if something is delivering messages. Configuration, not code.

3 · If you need multi-step work that survives a crash — and an agent does — adopt it rather than write it. Temporal, Restate, DBOS. Deduplication comes free, a crash resumes where it stopped, and a job can wait an hour for a human and wake up correctly.

That last clause matters more than the deduplication, because three of the parts described on this page exist largely because we do not have it:

What we builtWhat it re-implements
the duplicate-message guardrun-once semantics
saving the conversationcheckpoint and resume
waiting for an approvala long pause that survives a restart

Then why did we build it?

Deliberately — and it is worth saying plainly rather than defending. This is a reference implementation, and its job is to show what a system like this must contain. If the answer to “how do you guarantee it happens once” is “the workflow engine does it”, a reader learns nothing about what was needed. The output this whole programme claims to produce is the sentence “you chose X, and here is what X does not give you” — and nobody can write that sentence who has never held the problem.

For a real product the trade is the wrong way round. Adopt durable execution, let the queue deduplicate, make the actions harmless to repeat at the far end — and delete the guard entirely.

“Can I point the OpenAI SDK at Claude?” — yes, and it is a trap

Anthropic publishes a compatibility endpoint. Change the base URL and the key, and OpenAI-SDK code talks to Claude. The documentation is explicit about what it is for: testing and comparing models — “not considered a long-term or production-ready solution”.

Through it: prompt caching is not supported. strict is ignored, response_format is ignored, reasoning_effort is ignored, system messages are concatenated and hoisted to the front.

And the part that makes it a trap rather than a limitation — unsupported fields are silently ignored rather than rejected. You do not get an error. You get a normal-looking response, and a bill that never falls.

Worse: through the compatibility layer usage.prompt_tokens_details is always empty — which is precisely the field you would check to confirm caching worked. You cannot even verify the thing that is not happening.

“Can I use the Claude SDK but call OpenAI?”

No. The Anthropic SDK speaks one protocol and OpenAI's endpoint does not answer it. If you want one piece of code to reach many providers, that is what a gateway is for — and a gateway can only carry what every provider it supports has in common.

LangChain and LangGraph specifically

Both can call Claude. The question is not whether, it is what survives the abstraction.

LangGraph is the strongest option after plain Python, because you write the node body — so a node can call the Anthropic SDK directly and nothing is normalised away. You get orchestration from the framework and the full surface from the SDK.

Going through a framework's own chat class is usually fine and needs one check, which applies to any framework you evaluate:

# the only test that matters 1. can I attach a provider-specific field to the request? 2. can I see, in the response, that it took effect? # for caching that means reading back: usage.cache_read_input_tokens > 0

If the answer to (2) is no, you have no way of knowing whether the abstraction dropped it — and every one of these features fails silently.

The three rules

1. The loop and the client are independent. Any loop plus the native SDK gives you everything.
2. Calling Claude through an OpenAI-shaped request gets you the model, not the API.
3. A cross-provider interface carries the intersection. That is arithmetic, not a shortcoming of any particular library — and it is the real cost of portability.

Q6

So when do people deliberately call Claude from a non-Claude loop or client — and when is that right?

Often right. Almost never decided

There are good reasons and there is one very common bad one, and the difference is not the choice — it is whether anybody made it.

When it is genuinely correct

Portability is a requirement, not a preference. Procurement forbids single-vendor dependency. A regulator says some traffic stays in a region. An availability commitment means you keep serving when one provider is down. Cost routing sends easy work to a cheap model. In every one of those, a common interface is the product requirement and the intersection is the price of it. Paid knowingly, that is a good trade.

You are comparing models. This is what the compatibility layer is documented for. You want to change one variable — the model — not rewrite the client. Temporary by design, and correct.

The loop already exists and works. A pipeline written before Claude was in the picture. Adding one more model behind an existing abstraction is a day; rewriting the client is a quarter. Doing the cheap thing first is not a mistake — never revisiting it is.

The organisation already bought a cloud. Reaching Claude through Bedrock or Vertex is usually a procurement decision, not a technical one, and procurement outranks elegance more often than engineers like.

And the one people forget: the features may not apply to you. If your prompt is two hundred tokens and never repeats, prompt caching saves you nothing. If conversations are one turn, compaction is irrelevant. If everything is latency-sensitive, the batch API is useless. Paying an abstraction tax for a benefit you cannot use is not a trade-off — it is just noise.

When it is a mistake

Almost always the same shape, and it is not a bad decision — it is an absent one:

1. you use the compatibility layer to evaluate Claude ← correct 2. it works ← of course 3. it ships ← nobody decided this 4. six months later the bill is several times what ← and nothing it should be, because the stable prefix in front ever said so of every request was never cached once

What makes it hard to catch is the silence. Unsupported fields are ignored rather than rejected, and the field that would tell you — usage.prompt_tokens_details — is always empty through the compatibility layer. There is no error, no warning, and no way to check.

The two questions that decide it

1. Does my workload have a large, stable prefix that repeats? A long system prompt, a fixed tool list, a document every question is about. If yes, caching is very likely the single biggest cost lever available to you, and reaching it means the native surface. If no, the shim costs you little.

2. Is portability a requirement or a hope? A contract, a regulation, an availability commitment — those are requirements, and a gateway is the right answer. “We might want to switch one day” is a hope, and it is the expensive kind: you pay the intersection tax every single day for an option you may never exercise.

And the rule that makes either answer safe

Write down what you gave up. “We chose a gateway; it costs us prompt caching, strict schemas and thinking, and here is the number we measured.” A decision recorded like that can be revisited when the numbers change. One that was never made cannot — because nobody knows it happened.

HonestWhat is still wrong

A page that lists only the protections is a sales page.

  • Which messages have been handled is only remembered in memory. One process knows; a second copy of the agent would not, so a duplicate could still slip through a real deployment.
  • Two turns on one conversation can run at once, and one of them is lost. The overlap guard keys on the message id, not the conversation, so two tabs sending two different messages both pass it. Both read the same checkpoint, both write, and latest() keeps whichever landed second — the other turn's messages vanish while its effects stand. There is no version column and no lock in the state layer. The trigger module's docstring claims this case is covered; it is not.
  • An order has no items, so partial requests cannot be expressed. "Cancel one of these four" has no representation: cancel_order is whole-order and there is no item entity in either schema. Every guardrail passes a full cancellation, including the truthfulness check — the reply is accurate and the outcome is still wrong. It needs an order_item in the world file, not a better prompt.
  • Nothing checks that an action matched the request. The controls ask whether something happened and whether it was allowed. None of them holds the customer's intent to compare against, so a permitted, truthful, unwanted action is invisible.
  • The refund limit is checked against a number nobody verifies. The ₹10,000 threshold is compared against an amount the AI read from the conversation. The shop holds no record of what an order is worth.
  • Nothing is watching in production. Detailed traces are recorded and currently sent nowhere.
  • Speed under load is unmeasurable. One conversation at a time, and five separate requirements are waiting on it.
