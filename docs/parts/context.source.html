The Context Budget

When to act on context growth, the seven handlers that can act on it, and which compaction to reach for — under one constraint this agent already imposes and most designs ignore.

01When

"When the context is full" is the wrong answer, and it is the common one. By the time the window is full the only affordable move is the crudest one, because compaction itself needs room and a model call to run in. Growth is handled at five points, and four of them are before anything is full.

PointTriggerCostHere today
1 · Tool boundaryevery tool result, unconditionallyfree✅ max_tool_result_chars 8k
2 · Turn startduplicate or offloadable content presentfree❌
3 · Soft threshold~60% of budget, or a topic switcha model call❌
4 · Assemblyover the hard limitfree, lossy✅ assemble trims mid-out
5 · Checkpoint writeevery turnfree⚠️ recent capped, messages is not

Point 5 is the live bug. Conversation.messages has no cap, so a day-long conversation writes an ever-larger row on every turn and reads it back on the next — while the class docstring says keeping trace and checkpoint apart is *"what stops a checkpoint growing without bound." Trimming at assembly hides it from the model and not from the database.

02Seven handlers

They are not alternatives to choose between once. They compose, and the cheap ones should run first so the expensive one has less to do.

free · no model · lossy at the edge

1 · Bounder have it

Truncate one item before it enters. A 4 MB tool response is not a context problem yet — it becomes one the moment it is appended. Cheapest possible intervention, and the only one that needs no policy: it applies to everything, always.

free · no model · lossless

2 · Deduplicator

Collapse identical repeats — the same tool called with the same arguments three times, a system reminder re-emitted each turn. Pure win, no judgement required, and in tool-heavy agents it routinely recovers more than trimming would.

free at write · a round trip to read back

3 · Offloader

Move the payload to a store and leave a handle the model can re-fetch by tool call. Lossless, which no summariser is. The trade is latency and a step budget: the model must decide to look. Best for large, structurally separable artifacts — a full order history, a policy document, a diff.

free · no model · permanently lossy

4 · Trimmer / Evictor have it

Drop whole units by policy. This agent takes from the middle, keeping the earliest turns that establish the task and the latest that are being answered. Whole exchanges only — an earlier version dropped by index and orphaned tool calls in 8 of 55 turn/budget combinations, which every provider rejects.

free · no model · lossy by design

5 · Structurer / Notetaker

Maintain a running record of facts rather than transcript. Extract order ids, decisions, constraints, open questions into a small object carried forward; drop the prose that produced them.

This agent already has the primitive: TurnNote keeps route, result, intent and termination per turn in twelve slots. It exists for Tier 2 escalation rules, and it is the seed of the best context handler available here — because it is assertable, diffable, and cannot hallucinate.

a model call · lossy · provenance-sensitive

6 · Compactor / Summariser

Replace n units with generated text. The only handler that reduces size while keeping some of the meaning of everything it touched — and the only one with a correctness risk of its own. Section 03.

a retrieval per turn · lossy by relevance

7 · Selector / Retriever

Stop carrying history and fetch the relevant slice per turn. The right answer when the corpus is large, mostly irrelevant, and stable — product policies, past conversations, documentation. Wrong for the active transcript, where "relevant" is exactly what you cannot judge before answering.

03Kinds of compaction

"Compact" is four different operations with different failure modes. Choosing between them is the real decision; running one on a timer is not a strategy.

KindWhat it producesFails byRun it when
Extractive a subset of the original messages, verbatim dropping the one line that mattered default here. Cannot invent, and provenance survives intact per message
Structured a filled schema — entities, decisions, open questions a field the schema has no slot for agent loops, long tasks. Assertable and diffable; pairs with the Structurer
Abstractive new prose describing the old inventing, and flattening provenance only over content that is uniformly trusted
Rolling / recursive a summary that absorbs the next chunk each time drift — a summary of a summary, repeatedly very long sessions where old detail genuinely does not matter
Hierarchical summaries at several granularities, originals kept complexity, and cost when the model may need to zoom back in — pairs with the Offloader
Anchored a pinned set that is never compacted pinning too much always, as a modifier. Never a strategy on its own
The constraint that decides it here

This agent already states the rule that most compaction designs violate: "A summary inherits the provenance of its source. A summary of untrusted content is untrusted content."

Tool output is fenced and marked untrusted precisely so an instruction planted in an order note cannot be read as operator text. An abstractive summary that mixes a fenced tool result with the operator's own turns produces one blob that must be treated as entirely untrusted — which usually means it cannot do the job it was made for. The compaction step becomes the injection path the fence was built to close.

So: compact trusted and untrusted content separately, never into one summary, and prefer extractive or structured compaction, where each surviving unit keeps the provenance it arrived with.

Three rules any compactor here must obey

  1. Never touch the stable prefix. The system prompt is first and unchanged because any byte that moves invalidates every cached token after it — the largest cost lever available.
  2. Whole exchanges only. An assistant turn and the tool messages answering it are one indivisible unit. orphaned() already checks this on every assembly; a compactor must run through the same check.
  3. Anchor the goal and the last n turns. Compacting what the model is currently answering is how an agent forgets the question mid-task.

04Which handler, given what

The signal, not the size, picks the handler. Size only tells you that something must happen.

What is actually largeReach forNot
One enormous tool resultBounder, then Offloadersummarising it — the next call needs the same data
The same tool called repeatedlyDeduplicatortrimming, which drops distinct turns first
A long low-density conversationTrimmercompaction — nothing worth preserving is being lost
A long high-density conversationStructurer, then extractive compactionabstractive summary; the details are the value
Many loop steps in one taskStructurer (running scratchpad) + Offloadertrimming, which orphans the reasoning chain
A large stable corpusSelector / Retrievercarrying it at all
Topic switch mid-conversationCompact the closed topic, anchor the new onewaiting for a size threshold
Handoff to a personStructured compaction into the handoff payloadsending the raw transcript — AAC-0062

That last row connects to work already done. agent_state.escalations has a handoff slot in the design for exactly this: a reviewer picking up a ticket needs the structured facts of the conversation, not four thousand words of it. The context handler and the handoff payload are the same computation.

05What to build, in order

Cheapest and most certain first. Nothing here needs a model call until step 4, and step 4 may never be needed for a support agent whose conversations are short.

#StepCloses
1Bound Conversation.messages at checkpoint write, keeping whole exchangesthe live bug — unbounded durable growth, written every turn
2Measure before deciding: emit assembled size and turn count per call, alongside the AAC-0103 baselineyou cannot pick a threshold you have not observed
3Deduplicator over identical tool callsfree recovery in the tool-heavy case
4Structurer: promote TurnNote into a facts record carried forwardthe handler with no hallucination risk, and the handoff payload
5Soft threshold + extractive compaction, anchored and exchange-safethe first thing that costs a call
6Offloader for large artifacts, behind a re-fetch toollosslessness where summarising would be wrong
One thing to fix first, and one to accept

Fix: step 1. Everything else is optimisation; that one is a durable structure growing without bound on every turn.

Accept, for now: every budget here is counted in characters, not tokens. R-004 already recorded why — the provider choice means no count_tokens equivalent, so accurate counting is lost to the provider rather than to hand-rolling. Characters are a reasonable proxy for English prose and a poor one for JSON. Before tuning any threshold precisely, know that the ruler is approximate.
