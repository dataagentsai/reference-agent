Architecture reference · Tool selection

Agent Harness Selection

An agent is a loop: the model reads a context, asks for a tool, something runs it, and round it goes. That loop is about two hundred lines and nobody's advantage. Everything expensive sits around it — what enters the context window, surviving a crash, proving what happened, and stopping the run before it spends real money. Choosing a framework means knowing exactly which of those you are buying, and which residue is left for you.

01

The loop, and why it is the cheap part

An agent works like a competent assistant with a phone and no memory. You give it a task; it looks at everything it currently knows, decides the single next useful thing, and either answers or asks for something to be done. Something outside the model does that thing and hands back the result. Now it knows one more fact than before, and you ask again.

The most important architectural fact in the whole field is this: the model never acts. It only ever emits text, some of which happens to be a structured request. Every real effect on the world — a file written, a row deleted, an email sent — is performed by your code, because your code chose to honour the request.

That is what a harness is: the set of decisions about which requests to honour, with what context, under what limits, and with what record kept.

You can write this diagram in an afternoon. It will then fail in production for reasons that have nothing to do with the loop: the context grew past the window on turn 30, the process was redeployed on turn 12 and the run vanished, a tool returned a 60,000-token error page, nobody can explain what the agent did, it called the same API 400 times, and a user talked it into reading another customer's data.

Those six failures are six different concerns. Choosing a framework is choosing which of them you get help with — so the next thing to do is name them all.

02

The fourteen concerns

Every box in that diagram expands into work that somebody must do — a framework, a peripheral product, or you. These fourteen are the vocabulary for everything that follows. The weight on each is a rough multiplier for how much engineering it costs over two years.

Band 1 · Context

what the model is allowed to know
C1×1
Task intake & run contract

What a run is: inputs, goal, budget, caller, tenant. Without it you cannot bill, retry, audit or evaluate.

C2×1
Context assembly

Prompt engineering grown up — a data pipeline that runs before every single model call.

C3×3
Context lifecycle

What happens when the conversation outgrows the window. A framework with no opinion here demos beautifully and dies on turn 40.

Band 2 · Act

how the model reaches the world
C4×1
Model invocation

Routing, retries, failover, caching, structured output. The easiest thing on this list to buy outright.

C5×2
Tool surface

Defining tools, and — the underestimated half — shaping what comes back. An unbounded tool output poisons the window for the rest of the run.

C6×1
Execution & isolation

Running it somewhere it cannot hurt you, and classifying actions by side effect, because the model cannot be trusted to tell you which is which.

Band 3 · Control

who decides what happens next
C7×1
Control flow & termination

The loop, plus the conditions under which it stops. A missing stop condition is the most common way an agent becomes a bill.

C8×1
Delegation

Subagents and handoffs. The real reason to delegate is rarely intelligence — it is context hygiene.

C9×3
State & durability

Whether a run survives a restart, a pause, a week. The line between a demo and a system runs straight through here.

C10×1
Human-in-the-loop

Pausing for approval, and surviving the wait. A three-day approval is a durability problem wearing a UX hat.

Band 4 · Trust

whether anyone can rely on it
C11×2
Safety & policy

What goes in, what comes out, and which actions are permitted. The permission decision belongs outside agent code.

C12×2
Identity & authorization

Who the agent acts as. The least-solved concern in 2026, and every framework scores the same on it.

C13×3
Observability, cost & eval

Traces, money, and a graded test set. This decides whether you can improve the agent, rather than redeploy and hope.

C14×2
Lifecycle & operations

Versioning prompts, tools and graphs; rollback; tenancy. The unglamorous concern that decides whether you can have more than one agent.

The uncomfortable part. Rank these by cost and the top three are context lifecycle, durability, and observability. The loop itself — control flow — sits near the bottom. Yet almost every framework comparison you will read is argued on control flow: chains versus graphs versus handoffs. That is the cheapest concern on the list and the one you could write yourself in a day.

So: choose on C3, C9 and C13. Tolerate whatever control-flow shape comes attached.

03

The rubric: two scales, not one

A verdict expires; a rubric does not. Two of these four frameworks changed materially in the last year, so the durable artefact is the measuring stick, and the scores are the perishable part.

Ownership asks: if I adopt this and do nothing else, how much of the concern is handled? Score the default path, not the ceiling — every framework can do everything if you write enough code, and that is not what is being measured.

Scale 1 · Ownership
LevelNameTestWhat it costs you
0AbsentNo concept of this concern existsYou build it, and you build it around the product, which may fight you
1HookAn extension point exists, with nothing behind itYou build it, but there is a clean place to put it. For org-specific concerns this is the right answer
2PartialA working default that is known to need replacing at scaleFast to production, migration later. Fine if you know it is coming
3OwnedProduction-grade and opinionated; configured, not codedYou accept its opinion. Usually a good trade

Openness asks a separate question: can I remove it? These are independent — something can be excellent and unremovable, which is a manageable risk only if you noticed it. The rating applies to the seam, not the licence.

Scale 2 · Openness
RatingMeaningExit cost
OSpeaks a standard defined outside the vendor, with more than one real implementationDays — you change an endpoint
PProprietary interface, but a documented, genuinely used seam existsWeeks — you write an adapter
LIts concepts have leaked into your code, data or operating modelMonths, or a rewrite

The number you are actually computing is the build residue: the concerns you marked required that the candidate scores 0 or 1 on. A framework scoring 3 on ten concerns you do not need is worth less than one scoring 3 on the three you do.

04

The four, and what each is really selling

These are four products for four different anxieties. That is why "which is best" has no answer, and "which anxiety is mine" does.

LangChain

Sells reach — it talks to everything.

Owns
Provider integrations, loaders, splitters, vector-store interfaces, a large tool catalogue.
Breaks at
Abstraction drift — uniform until you need a provider-specific feature — and attribution when something goes wrong deep in a composition.
Use as
A library of adapters, kept at the edges. Its own agent constructor now runs on LangGraph underneath, so it is the front door, not the engine.

LangGraph

Sells memory of what happened — state that survives and replays.

Owns
Control flow, durability, human-in-the-loop, replay. Checkpoints every transition into your Postgres.
Breaks at
Open-ended exploration, which ends up inside one node that is really a loop. And state design becomes a real design problem you now own.
Use when
The work has shape: defined steps, approvals, long horizons, or a need to answer "what did it do at step 9".

Claude Agent SDK

Sells a finished loop — including the context management almost nobody else takes seriously.

Owns
Context lifecycle (compaction, subagent isolation) and execution with a real permission model. Native MCP.
Breaks at
Model coupling — the loop is tuned to one model family, which is the product — and workflows needing a guaranteed fixed path.
Use when
The work is environment-heavy and the path cannot be drawn in advance: code, files, ops, document pipelines.

OpenAI Agents SDK

Sells simplicity — the fewest concepts to hold in your head.

Owns
Handoffs between specialists, guardrails as a first-class idea, tracing out of the box. Gained sandboxes, durability and subagents in April 2026.
Breaks at
Growth. Little is imposed, so little is solved; past routing you find yourself building orchestration on a library that has opinions but not machinery.
Use when
Conversational routing, voice, multi-provider work — and when your residue is genuinely small.
05

Fifteen agents, fifteen stacks

Everything above is a rubric, and a rubric is only trustworthy if you can watch it being applied. So here it is applied fifteen times, across fifteen genuinely different shapes and domains — ten that choose a harness, five that need no framework at all, and one that is not an agent. Each is worked the same way — and the repetition is the point. By the fourth one you should be able to predict the answer, which means you have the method rather than the conclusions.

Every case answers the same five questions first, before any design work: how long a run lasts, whether the path is known in advance, who is waiting, what it changes in the world, and how many different users it acts for. Those five facts do most of the deciding.

01

Billing support agent

B2B SaaS customer support

Answers questions about invoices, usage and plan limits. Can issue a refund below a threshold; anything larger goes to a human.

  • Run 2–5 minutes
  • Path roughly known
  • Waiting the customer, in chat
  • Changes refunds — real money
  • Users thousands, each seeing only their own account

C5 toolsC11 policyC12 identityC13 observabilityC9 durability — Won't

OpenAI Agents SDK with a handoff to a refunds specialist and an escalation path to a human queue · LiteLLM · billing tools over MCP · the refund threshold enforced in a policy check at the tool boundary, never in the prompt · traces carrying the account id so tickets and traces can be joined.

Why not the others. LangGraph gives you durability you marked Won't, and a graph for a three-step conversation is ceremony. The Claude SDK's strengths are for an agent with a computer, and there is no computer here.

Breaks first: the refund threshold living in a prompt. The model honours it in testing and gets talked past it in production — and that incident has a rupee value attached.

02

Spark cost analyst

Data engineering — your own CostIntelligence work

Reads Spark event logs and Delta metadata for last week's jobs, finds the expensive ones, works out why — skew, small files, a cartesian join, a Python UDF in a hot path — and writes up the diagnosis with evidence.

  • Run 20 min – 2 hours
  • Path unknown — "work out why" is the part you cannot specify
  • Waiting nobody; read in the morning
  • Changes nothing — read-only
  • Users one team

C3 context lifecycleC5 toolsC6 executionC13 observability

Claude Agent SDK, for one reason above all: a subagent per suspicious job, each reading logs in its own context window and returning six lines. The parent never sees the hundred megabytes · your existing rule_skew_detection logic wrapped as MCP tools rather than re-derived each run · read-only container mounts · large outputs to object storage with a pointer in the context, never the content.

Why not the others. LangGraph would force you to draw a diagnostic path you specifically do not have — you would end up with one node containing a loop, paying for a graph you are not using.

Breaks first: a tool that returns an unbounded log slice. This agent's economics are context economics, and one careless tool contract undoes the harness choice made for exactly that reason.

03

Invoice reconciliation

Finance operations

Matches supplier invoices against purchase orders and goods receipts in the ERP. Posts the matches; investigates the discrepancies and routes them to the right approver by value.

  • Run minutes of work, then days waiting
  • Path known, and auditors require that it be
  • Waiting an approver, by notification
  • Changes financial entries — hard to reverse
  • Users many approvers, different authority limits

C9 durabilityC10 human-in-the-loopC11 policyC13 provenance

LangGraph checkpointing to your own Postgres — the graph is simultaneously the implementation and the process documentation an auditor can read · OPA holding the approval matrix, so authority limits are one auditable artefact · approvals into the workflow tool finance already uses, never a chat message.

Why not the others. Model-driven autonomy is the wrong control model — you do not want an agent finding a creative path through a financial control. The OpenAI SDK's durability is newer than a checkpointed graph, and this is not the place to be an early adopter.

Breaks first: a graph definition changing while runs are in flight. You will deploy while forty invoices sit at "awaiting approval" — test that deliberately before go-live.

04

Dependency upgrade agent

Developer tooling — internal platform team

Takes 200 internal repositories from Python 3.9 to 3.12. Per repo: read the code, change what needs changing, run the tests, fix what broke, open a pull request for review.

  • Run 10–90 min per repo, times 200
  • Path unknown — every repo breaks differently
  • Waiting nobody
  • Changes branches and PRs; nothing merges unreviewed
  • Users one platform team

C3 context lifecycleC6 isolationC5 toolsC1 run contract

Claude Agent SDK — its home ground, an agent with a computer and an unspecifiable path · one sandboxed container per repo, no network except the package index, destroyed after · the orchestration across 200 repos is not a graph and not an agent: it is a work queue with a row per repository and a status column.

Why not the others. LangGraph has nothing to draw: the per-repo path is unknown and the cross-repo fan-out is a queue, which Redis does better than a graph runtime.

Breaks first: cost, with no warning. 200 repos × 90 minutes of autonomous exploration is real money and nobody is watching. This is the clearest case for building the budget governor before the first production run.

05

Clinical protocol document check

Pharmaceutical regulatory affairs

Checks a trial protocol against a regulatory checklist — required sections present, endpoints defined consistently, statistical plan matching the objectives — producing findings with a citation each.

  • Run minutes
  • Path completely known — the checklist is a controlled document
  • Waiting a reviewer, later
  • Changes nothing
  • Users a regulatory team

C13 provenanceC14 versioningC2 parsing

No harness at all — this is a pipeline, not an agent. Parse the document, then one scoped model call per checklist item, collect, assemble the report. LiteLLM for the calls, the checklist versioned in Git, OpenTelemetry because you still want to see what happened, and an eval set of previously-reviewed protocols with known findings.

Why not the others. Every framework here would add a control loop whose entire value proposition — the model decides what to do next — is the property this domain forbids. Reproducibility is the deliverable.

Breaks first: nothing technical. What breaks is the review, when someone asks why a finding appeared and the answer involves the word "decided".

Fixed path + regulated output + no side effects means a pipeline. A selection method that never rejects the whole category is not a method.

06

Incident triage assistant

Cloud operations — the read-only shape

When an alert fires, it gathers context before a human arrives: recent deploys, error-rate change, upstream services, matching past incidents. Posts a summary within two minutes.

  • Run under 2 minutes, and the deadline is real
  • Path unknown — it follows evidence, like a person
  • Waiting an on-call engineer, at 3am, impatiently
  • Changes nothing — strictly read-only by design
  • Users an ops team

C5 toolsC3 context lifecycleC7 termination

Claude Agent SDK for parallel subagents — one on deploys, one on metrics, one on past incidents, all at once, each returning a short finding · a hard wall-clock budget that terminates and reports what it has · no sandbox needed, which is a genuine saving: read-only tools with no code execution removes an entire seam.

Why not the others. LangGraph would impose a diagnostic sequence, and the whole value is following the evidence where it leads.

Breaks first: trust, quietly. Wrong twice at 3am and engineers stop reading it. The eval set here is replayed past incidents with known causes, and it is the only thing standing between this and abandonment.

Read-only is the cheapest security posture available. It costs the ability to act and removes policy, sandboxing and approval from the Must list.

07

Clinic appointment line

Healthcare front office — voice

Answers the phone. Books, moves and cancels appointments, checks what a patient is due for, hands off to a human for anything clinical.

  • Run 2–4 minutes of conversation
  • Path known — book, reschedule, cancel, escalate
  • Waiting a patient on the phone, where two seconds is a long silence
  • Changes the appointment book; sends confirmations
  • Users every patient, and it is health data

C4 latencyC8 handoffsC11 policyC12 identity

OpenAI Agents SDK, where voice and handoffs are the native shape and the routing model matches the domain word for word · guardrails on both sides: a topic boundary routing anything clinical to a human, and structured validation of every booking before it is written · traces scrubbed of health identifiers before they leave your boundary, which is one adapter decision made once.

Why not the others. The Claude SDK is built for a long exploration with a computer; neither exists here, and the latency budget punishes a harness that likes to think.

Breaks first: the clinical boundary, under an unusual phrasing. "Should I be worried about this pain" is not a scheduling question — and a guardrail catching it is a control, while a careful sentence in the prompt is not.

08

Competitive research writer

Market research / strategy

Given a question — how are the four main vendors pricing seat-based versus usage-based — it searches, reads, cross-checks, and produces a brief with sources.

  • Run 1–3 hours
  • Path unknown — what it finds determines what it looks for next
  • Waiting nobody
  • Changes nothing, but publishes assertions someone will act on
  • Users a small team

C3 context lifecycleC8 delegationC13 provenanceC11 input safety

Claude Agent SDK with a subagent per research thread, so four investigations do not contaminate each other · a sandbox with an egress allowlist, because fetched web pages are hostile input by default and this is the classic injection route · evidence accumulated as a first-class list on the run, because provenance is nearly free if designed in and very expensive to reconstruct later.

Why not the others. LangGraph cannot draw a research path that does not exist yet; the OpenAI SDK leaves the three-hour context problem to you.

Breaks first: confident synthesis of two sources that disagree. Not a crash — a well-written brief with a wrong number in it, which is why the eval set must grade sourcing and not only fluency.

09

Personal assistant over mail and calendar

Consumer productivity

Reads a person's mail and calendar, drafts replies, schedules things, reminds them what they said they would do, and remembers their preferences over months.

  • Run seconds per interaction — but the relationship lasts years
  • Path partly known; a few intents, loosely followed
  • Waiting the user, usually
  • Changes sends mail as them — socially irreversible
  • Users thousands, each with their own mailbox

C12 identity — the product itselfC5 toolsC11 policyacross-run memory

LangGraph, for a reason specific to this shape: per-user state persisting across months belongs in a checkpointed store you own, and the intents are few enough to draw · per-user OAuth tokens in a secret store, injected by the harness at call time and never held by the tool · "send" always confirms until the user turns that off, per recipient · row-level security everywhere, tenant key threaded from intake so it is structurally impossible to forget · memory as a schema you designed, with deletion semantics that actually work.

Why not the others. No harness solves identity — all four score the same — so it is not the deciding factor. LangGraph wins on durable per-user state, and creative autonomy through someone's mailbox is a bug, not a feature.

Breaks first: cross-account leakage, by the most mundane route — a retrieval query or memory write missing its user filter. Here the identity gap is not a seam to design for later; it is the first thing to build.

10

Pipeline self-healing agent

Data platform operations

When a scheduled job fails at 2am it diagnoses the failure, and for a known class of causes — a transient cluster issue, schema drift needing a documented backfill, a stuck lock — applies the fix and restarts. Anything else wakes a human.

  • Run minutes to hours including backfills
  • Path the fixes are known; the diagnosis is not
  • Waiting nobody at 2am, which is the entire risk
  • Changes production data — can make things much worse
  • Users one platform, several data domains

C11 policy — strictest hereC9 durabilityC13 observabilityC3 context lifecycle

Both harnesses, deliberately. LangGraph owns the outer process, because it genuinely has shape: detect → diagnose → classify → if known and low-risk apply, else escalate → verify → report. That graph is the safety argument, written down, and it is what you show the data owners when they ask why they should permit this. Inside the single diagnose node, a Claude Agent SDK agent explores freely — reads the logs, checks upstream tables, compares against the last good run — and returns a structured verdict: cause class, confidence, evidence, proposed fix. It does not act. The graph decides and the graph acts. Around both: an allowlist of fixes, each with a documented blast radius and a rollback; OPA deciding which fixes are permitted in which domain; production deletes never permitted at all.

Why this is not over-engineering. Two ×3 concerns — durability and context lifecycle — and no single product scores 3 on both. The seam is one node boundary with a schema crossing it. You are not integrating two frameworks; you are calling one from inside the other.

Breaks first: a fix that works and should not have been applied. The dangerous failure is a correct-looking diagnosis of the wrong root cause, confidently fixed — which is why the verdict carries a confidence and the graph treats low confidence as escalation, not as a hint.

Pull request review bot

Developer tooling · situations 1 and 3

On every pull request it reads the diff, pulls two or three files for context, and comments on what a linter cannot catch — a schema change without a migration, a response shape changed without a version bump, a test that asserts nothing.

  • Run 30–90 seconds
  • Path roughly known
  • Waiting the PR author, loosely
  • Changes comments only; nothing merges
  • Users one org, one bot identity

C5 toolsC13 cost

A plain loop — about 200 lines inside the webhook service you already run: message list, four tools, step cap of eight, errors returned as observations. Gateway, one OTel span per run carrying the PR number and cost.

Why no framework. Every ×3 concern is a Won't — nothing to compact in 90 seconds, nothing to checkpoint because the webhook redelivers, no human pause. Trigger to adopt one: the day you want it to run the tests in a sandbox and iterate on failures.

Breaks first: cost through volume. Thousands of runs a week turns a trivial per-run cost into the quarter's budget.

The learning build

Your own spark-cost-agent repo · situation 2

A deliberately hand-rolled harness whose purpose is to make observability, evaluation and cost accounting visible, by building them rather than importing them.

  • Run minutes
  • Path partly known, and it does not matter
  • Waiting you
  • Changes nothing

Two escape hatches, then three questions

Six of fifteen use no framework at all — five plain loops and one pipeline. That proportion is roughly what an honest portfolio looks like, and it is the most under-reported fact in this field: most published examples come from cases 1–10 because those are the ones with something to demonstrate.

0

Does the path need deciding at run time at all?

If the sequence is fixed and the output is regulated, you want a pipeline with model calls inside it, not an agent (case 5). A loop that decides what to do next is a liability when reproducibility is the deliverable. Ask this first, every time, and be willing to answer "no agent".

0b

Does it need a harness at all?

The loop is two hundred lines; a framework sells compaction, durability, human-in-the-loop and replay. If all four are Won'ts — short run, read-only, or living inside something that already owns durability — a plain loop is correct engineering, not a shortcut. The tell: four of the five plain-loop cases run inside an existing runtime — a webhook service, a queue consumer, an Airflow task, the user's own terminal.

1

Is the path known in advance?

No means an autonomous harness with strong context management (2, 4, 6, 8). Yes means a graph (3, 9) or a light routing framework (1, 7). This one question accounts for most of the table.

2

Does the run outlive the user's attention?

Days of waiting, approvals or backfills make durability a Must and the graph earns its keep (3, 9, 10). A user sitting in a chat window makes durability a Won't, and buying it is buying weight you never use (1, 7).

3

Does it act for many users with different permissions?

If yes, identity stops being a row in the matrix and becomes the architecture (9, and to a lesser degree 1 and 7). No framework helps — they all score 1 — so this question does not choose your harness. It chooses your first month of engineering.

Five things the ten show that the matrices could not

  1. The harness repeats; the peripherals do not. Four use the Claude Agent SDK and three use LangGraph, yet no two stacks here are the same. The differences are sandbox posture, policy strictness, whether provenance is first-class, and where the budget is enforced. The framework is the least differentiating decision on this page — the opposite of where attention usually goes.
  2. Read-only is the cheapest security posture available. Cases 2, 6 and 8 change nothing, and that single fact removes approval gates, destructive-action classes and most of the policy surface from their Musts. Where the domain allows a read-only first version, take it — adding writes later with a graph around it is exactly the step from case 2 to case 10.
  3. Nobody watching is a cost problem before it is a safety problem. Cases 4, 6 and 10 run unattended, and two of the three likeliest failures in this document are financial: 200 repos of unbounded exploration, and a diagnosis loop that will not converge at 2am.
  4. What breaks first is almost never the framework. Re-read the ten: a threshold in a prompt, an unbounded tool result, a graph version changing under in-flight runs, cost with no cap, a guardrail that was only a sentence, a wrong number confidently sourced, a missing tenant filter, a confident diagnosis of the wrong cause. Every one is a contract, a policy or a limit — the things section 12 says are yours.
  5. The composite is rare and real. One in ten needed two harnesses, for a nameable reason. If you reach for two on a second agent, check you are not reaching for interest rather than necessity.

Using this on your own agent: answer the five shape questions before reading anything else, then questions 0 through 3 in order. You will have a harness in about ten minutes, and it will be right often enough that the remaining time goes where it always belonged — the tool contracts, the context policy, the budget, and the twenty evaluation cases.

06

When to use no framework at all

Section 12 lists "the agentic loop" under things you must not build, and that is stated too flatly. It is right about the danger — teams who set out to own the loop usually end up owning compaction, checkpointing and replay too, which is a framework with one maintainer and no tests. It is wrong as a blanket rule.

The loop is genuinely small. Assemble a message list, call the model, check whether it asked for a tool, run it, append the result, repeat until it answers or you hit a cap. That is 150 to 250 lines of Python including error handling, and there is nothing clever in it. So the loop is not what a framework sells you — it sells the machinery around the loop: what stays in the window as the run grows, surviving a restart, pausing three days for a human, replaying a run to see what happened.

Which makes the decision one question: do I need the surroundings? If yes, adopt a framework — the loop was never the point. If no, write the loop, because you would be adopting a framework for machinery you never touch.

Five positions, not two

"No framework" has two distinct meanings and people conflate them. Position 2 deserves more attention than it gets: the provider SDKs now ship a tool-runner that executes the loop over tools you define — no framework, no hand-rolled loop, no orchestration opinions imposed. For a lot of simple agent work it is the right answer, and it is overlooked because it is not marketed as a framework.

Six situations where a plain loop wins

1

Short, stateless runs

Three to eight tool calls, done in under a minute, where a crash means an acceptable retry. Every ×3 concern is a Won't: nothing to compact because the run is short, nothing to checkpoint because a retry is cheap. This is the most common case, and the one where framework adoption is most often reflexive rather than reasoned.

2

You are learning the mechanics

You cannot form an opinion about context policy, budget enforcement or trace design while a framework quietly handles all three. Build it by hand once and the fourteen concerns stop being a list and become things you have felt — after which you can judge frameworks on what they do rather than on their documentation.

3

Something else already owns durability

Inside a Temporal workflow, an Airflow or Dagster task, a Kubernetes job, a queue consumer. A framework checkpointer layered inside a durable engine means two systems both believing they own restart semantics, and when they disagree on a retry after partial failure the debugging is genuinely unpleasant. One durability system per run.

4

The control flow is genuinely idiosyncratic

A specific repair-and-retry protocol, an unusual escalation rule, a loop interleaved with an existing event system. Honest test: would you spend more time fighting the framework's shape than owning two hundred lines? Be careful here — this is the reason people give most often and justify least. If you cannot name the specific thing the framework will not let you do, you do not have this case.

5

You are shipping a library

Other teams import your code, so a framework dependency is a decision you are making on their behalf, version conflicts included. Your dependency surface should be the model client and nothing else.

6

It works and nobody is changing it

A single-purpose agent in maintenance. Framework churn — and these frameworks churned significantly in the last twelve months — is pure cost with no offsetting benefit.

The distinction people get wrong

Hand-rolling the loop is not hand-rolling the stack. Owning the control flow does not mean owning everything else, and every peripheral in section 08 applies unchanged.

Even with a plain loop you still want the model gateway, because provider lock-in and budgets were never loop concerns; MCP for tools, because tools outlive the loop whether you wrote it or not; OpenTelemetry traces, because writing your own trace format stays on the do-not-build list; and all of section 12 — run contract, context policy, budget governor, eval cases — which was always yours regardless.

A plain loop with a gateway, MCP tools, OTel traces and twenty eval cases is a serious system. A plain loop with direct provider calls, bespoke tool wiring and print statements is a prototype that will be mistaken for one.

What the loop actually contains

Seven things, so you can judge the size of the commitment. Points 4, 5 and 6 are what separate a loop that survives production from one that does not — none of them difficult, all of them easy to leave out when the demo works.

  1. A message list, and the rules for what goes in it.
  2. A tool registry — name to callable, plus the schema shown to the model.
  3. The loop — call the model; if it requested tools, dispatch and append; otherwise return.
  4. A step cap and token budget, checked every iteration. Not optional.
  5. Errors returned as observations rather than raised. The most important detail and the one most often missed: a tool failure is information the model can act on, and a crash is not.
  6. Truncation of tool results before they enter the message list.
  7. A trace span per iteration, carrying run id, tokens and cost.

When to stop hand-rolling

Write the trigger down on the day you start. Adopt a framework the moment any of these becomes true — each is a subsystem, and each is available off the shelf from people who work on nothing else.

  • A run must pause for a human and resume after a process restart. You are now building a checkpointer.
  • Context management must be cleverer than dropping the oldest messages. You are now building a compactor.
  • You need subagents with independent context windows. You are now building delegation.
  • You need to replay a past run to debug it. You are now building time travel.
  • More than one person maintains the loop, and they disagree about its shape.

The failure mode this is really about is drift. You write a clean loop in week one. In month three you add a crude summariser because runs got longer. In month five a state table, because a run died halfway. In month eight someone asks what the agent did last Tuesday and you add a JSON log with your own field names. Now you maintain a half-built framework with one user, no tests and no upgrade path — and every piece of it exists, finished, in the projects you rejected.

The trigger list is there to catch that at month two rather than month eight. A plain loop is a decision with an expiry condition, not a permanent position. Written down it is good engineering; left implicit it is how teams end up maintaining a framework by accident.

Applied to the ten agents

Hand-roll the incident triage agent (case 6) in a first version — runs under two minutes, read-only, hard deadline, and a crash means the engineer reads the dashboard themselves. Every ×3 concern is a Won't. The trigger to adopt a harness is the day you want parallel subagents for the deploy, metric and past-incident lookups, which is a real requirement and a reason to switch rather than a reason to have started with a framework.

Never hand-roll the invoice reconciliation agent (case 3). The moment "pause for three days and survive a deployment" appears, you are writing a checkpointer — and the graph runtime that does it properly is a weekend of learning against a quarter of building.

09

Pick by archetype, not by product

Same scores, three different Must lists. This is the comparison that actually decides things — which is why the step before scoring is marking each concern Must, Should or Won't, with at most five Musts. Do that before you look at any product, or the products will do it for you.

Two harnesses is a legitimate answer. A realistic task often mixes archetypes — a defined process containing open-ended exploration. Put the process in a durable graph and the exploration inside a node, delegated to an autonomous harness that returns a structured result. The two answer two different ×3 concerns, durability and context lifecycle, and no single product scores 3 on both.

It stops being justified when the exploration fits in one context window, or when the process has no approvals and no long waits. Reach for it because you wrote down two Musts and found no product covering both — not because it is interesting.

What is left for you to build

You build the control plane, the tool contracts, and the definition of quality. Everything else you assemble. Notice the pattern across both columns below: build what encodes your domain, risk appetite and standard of good; assemble everything that is the same for everyone. That is the whole buy-versus-build test.

Build — eight things

  1. Run contract. One table, ten columns, written at intake. Without it you cannot say what a run is, so you cannot bill, retry, audit or evaluate one.
  2. Tool contracts and the domain tool surface. Your tools are your domain — the largest and most durable work here, and the one thing that cannot be copied by someone who read the same documentation.
  3. Context policy. One page, written before building, saying what is pinned, summarised and dropped. Frameworks supply the mechanism; the policy is domain knowledge.
  4. Policy and permission model. Your risk appetite. A vendor default is somebody else's risk appetite applied to your liability.
  5. Evaluation cases and graders. Twenty real cases in your repo is a week's work and the highest return on this page. Ten real failures beat a thousand invented ones.
  6. Budget governor. Enforcement, not reporting: the budget rides on the run and is checked at the loop boundary.
  7. Human interface. Where approvals land, and where somebody reads ten traces a week and labels the failures.
  8. Adapters to your world. One per external system, with tenancy and identity threaded through structurally, so they cannot be forgotten.

Do not build — and what to use instead

  • The agentic loop. Two hundred lines, then you own compaction, retries and checkpointing forever. → a framework
  • A trace format. You will reinvent OpenTelemetry badly and be unable to use anything built for it. → OTel behind one adapter
  • Model client wrappers. Your "thin wrapper" does not stay thin. → a gateway
  • A vector database. A decade of research you need not repeat. → pgvector
  • A sandbox runtime. Security engineering with a long tail of escapes. → gVisor or Firecracker
  • A durable workflow engine. Exactly-once under partial failure is genuinely hard and genuinely solved. → checkpointer, then Temporal
  • A prompt DSL. Every team builds one and regrets it: an untested language with one user. → files in Git
  • Your own tool protocol. Competing with a standard every framework already speaks. → MCP

Sequence matters, or you build some of it twice

Before the first agent: the run contract, the tool contract template, the context policy — these are contracts, and retrofitting a contract means touching everything that ignored it. Before production: the policy model, the budget governor, and the first twenty eval cases, which prevent the three expensive first incidents — the unauthorised action, the runaway bill, the undetected regression. First month live: the human interface and trace review, designed against real traffic rather than guessed at. Then forever: eval cases grow from production failures and the tool surface grows with the domain. Those two are not projects that finish; they are the system's metabolism.

Lock-in, measured in days

"Open architecture" is usually taken to mean "use open-source components". That is a category error. An Apache-2.0 framework whose data model has spread through four hundred of your files is locked — the licence permits you to leave, the architecture does not. A paid, closed vendor you reach only through an OpenTelemetry endpoint is open: leaving costs one config change.

Open architecture is a property of your seams, not your components' licences. The measure is engineer-days to replace. Vague discomfort about lock-in is not a decision input; a number is.

Three things that stay yours, always

Your state — run records and checkpoints, in a database you operate and a schema you can read without the vendor. Your traces — a standard format, your storage, your retention. Your tool contracts — behind MCP or your own interface, never inside a framework's decorator. Everything else is negotiable; these three cost almost nothing to hold at the start and cannot be recovered later.

Where lock-in is the right call

Refusing all lock-in has its own pathology: you abstract five providers and get the intersection of their features, which is worse than any one of them. Lock in deliberately when the exit cost is written down, the capability is genuinely differentiated, and the alternative is building it yourself. Model-family coupling in an autonomous harness qualifies — the tuning to one model's behaviour is the product, and abstracting it away leaves you with the generic loop you were trying not to build.

The summary rule: lock in at the layer, never at the seam. Let a framework own its layer completely and use its idioms properly — that is how you get the value you paid for. A framework used idiomatically behind contracts you own is a few weeks to replace. A framework used defensively through a homemade abstraction is slow to build, painful to debug, and usually harder to leave than the thing you were protecting yourself from.

Running an actual selection

About three days for a real decision, most of it in steps 1, 2 and 6. Less produces a choice made on tutorials; more produces a choice made on documentation, which is barely better.

1

Write the loop in prose

One page, ordinary sentences, before looking at any product. If you read documentation first, the products supply your requirements — you will need handoffs because handoffs were on the front page.

2

Mark the fourteen concerns Must / Should / Won't

At most five Musts. The most valuable marks are the Won'ts, because they let you reject a capable product cleanly.

3

Score three candidates, no more

The default path only. From documentation and one real attempt — never from a blog post, this page included.

4

Compute the build residue

Musts scoring 0 or 1, plus the gaps that apply to everyone. Under two weeks means you are underestimating identity, evaluation and cost.

5

Check the exit cost of every 3

A concern scored 3 is a concern you stop thinking about, which is exactly where lock-in accumulates unobserved.

6

Pilot two tasks: the representative one and the one that breaks things

Every framework demos well on the first — that is what the documentation was written for. The differences appear only in failure, and failure is where you will spend your production life.

7

Write it down, including the revisit trigger

"We chose the light framework; we revisit if runs exceed an hour or approvals enter the flow." The trigger is what turns a decision into an architecture.

The anti-patterns worth memorising

  1. Choosing on the control-flow argument — a ×1 concern with a one-point spread.
  2. Deferring observability to "after launch" — launching blind, then instrumenting a system already under load.
  3. One service account for all users — the tutorial default, and the most common serious security flaw in deployed agents.
  4. Assuming a pause primitive means human-in-the-loop is solved — that is the technical half; the queue, deadline and escalation are yours.
  5. Abstracting over every framework to stay neutral — you get the intersection of their capabilities and a harder migration than the one you feared.
  6. Adopting a durable execution engine on day one — real distributed-systems cost, for a chatbot.
  7. Treating memory as a product rather than a policy — buying a component before deciding what is remembered, for how long, and deleted on what request.
  8. Adding a second product to a filled seam — replacing the default is a decision; running both is an accident that becomes permanent.

All of them are versions of one mistake: selecting on the demonstrable and paying on the operational. You will live in the operational phase roughly a hundred times longer than in the demo.

If you have an hour, not three days

Take the default for your archetype from section 09. Put a gateway in front of the model on day one. Emit OpenTelemetry traces from the first run. Write the run contract and tool contract template before the first tool. Twenty evaluation cases before production. Write down the revisit trigger. That covers most of the value; the rest is in piloting the task that breaks things, which is the step to add back first.

Knowledge graphs, and the conversational data UI

A knowledge graph is the most over-prescribed component in this field. It is intellectually satisfying, it demos well, and it is frequently a year of work that a retrieval index would have covered in a fortnight. Two tests decide it.

1

Is the question a traversal?

"What does finance mean by net revenue?" is one lookup — retrieval answers it and a graph adds nothing. "If I change the schema of orders, what breaks?" is a traversal across three views, two dashboards and a regulatory report. No document contains that answer and no amount of embedding similarity produces it. The tell is the phrase "what depends on".

2

Does the graph already exist?

This test kills most knowledge-graph projects, and it should. Table lineage, foreign keys, service dependencies and code imports are almost always derivable from your dbt manifest, your information_schema, your catalogue, your OpenLineage events, your source code. Generate the graph from the systems of record; never hand-author what you can extract. A hand-maintained graph rots the moment somebody ships a schema change, and then it is worse than nothing because it is confidently wrong.

Agent 16 · a conversational UI over a database or Unity Catalog

The hard part is not generating SQL — models are good at SQL. The hard part is that your schema does not contain the information needed to answer the question correctly. A column called amt does not say whether it is gross or net, whether refunds are included, which of three date columns means "when it happened", or that joining to dim_team silently drops contractors. A human analyst knows those things. They are not in the schema — they are the product.

That has a direct consequence: most of this system should not be agentic. Retrieval, validation and execution are deterministic steps. The model writes one query and, at most, repairs it once. The loop is short and tightly fenced, not exploratory.

1

Metadata ingestion

Unity Catalog API or information_schema, the dbt manifest, and — the most underused source in the building — query history, which shows the join paths and filters people actually use.

2

The semantic layer — what you build

YAML in Git, reviewed like code: business synonyms, metric definitions as SQL, correct join paths, always-implied filters, value enumerations, grain and time semantics. Cube, dbt MetricFlow or Malloy if you would rather not invent the format. The strongest version has the model emit a semantic-layer query rather than raw SQL — then it cannot write a wrong join, because it never writes joins.

3

Retrieval

pgvector plus keyword search over the semantic layer, returning candidate tables, matching metrics, and three to five similar question → SQL examples. The few-shot examples do more for accuracy than any prompt engineering, and they arrive free from step 7.

4

Generation

One constrained model call. Low temperature. The least interesting layer in the system, which is the point.

5

Validation — the deterministic gate

Nothing reaches the warehouse unvalidated: SQLGlot parse in the target dialect, SELECT-only, table allowlist, injected LIMIT and timeout, then EXPLAIN or dry-run — which on Databricks or Snowflake gives a cost estimate before you spend anything. Failures return as a repair instruction, capped at one or two attempts; an uncapped repair loop against a warehouse spends money fast.

6

Execution — as the user, not as the service

The most important decision here. Pass the asking user's identity through so Unity Catalog enforces their grants, row filters and column masks — or connect as a role with row-level security in Postgres. Do this and C12, the concern every framework scores 1 on, is solved by the warehouse, which has spent a decade on it. Two users asking the identical question correctly get different answers, and nothing in the agent layer needs to understand your permission model. The credential is read-only at the database level — not "we only generate SELECTs", a role physically incapable of writing.

7

Rendering and feedback

Always show the SQL — non-negotiable for trust — plus the interpretation in words, so a wrong assumption is visible without reading SQL. Every correction becomes a few-shot example and an evaluation case. That loop is what makes the system improve rather than merely exist.

Case 17 · the reference support agent

This one is not hypothetical. It is a real agent in ~/reference-agent, whose stack was decided on 5 September 2026 and written down in that repo. It is the most useful case in the set, because it disagrees with this folder's own advice in two places and is right to do so.

What the agent is

A customer support chat for an online shop. A customer types a question — "where is my order" — and the agent looks the order up and answers. Sometimes the customer wants a refund. Refunds move real money, so a person has to approve one before it happens, and that person might take an hour to get to it. Hold on to that last detail, because it drives most of what follows.

Decision 1 · two kinds of work, so two mechanisms

The agent has two jobs inside it with completely different characteristics.

Answering a question is fast work. The customer is waiting and expects a reply in about two seconds. If the server crashes halfway through, nothing bad happens — they ask again and get an answer.

Getting a refund approved is slow work. It might sit for an hour waiting for a human. During that hour the server could be restarted or redeployed. And when the approval finally arrives, the refund must be paid exactly once — never twice, never not at all.

You cannot serve both with the same machinery, so the design splits them.

The workThe mechanism
The chat turnA plain Python loop, written by hand — about 350 lines, already in the repo
The refund approvalTemporal — software whose whole job is remembering where a long process got to, surviving restarts, and guaranteeing a step runs exactly once

Why not put everything on Temporal? It would add a network round trip and real operating weight to every single chat message, to protect against a crash that costs nothing when it happens.

Why not do everything with the plain loop? A plain loop lives in the web server's memory. Restart the server and a refund that had been waiting fifty minutes is gone — or worse, gets re-run and pays the customer twice.

The principle underneath: durable execution is worth its cost when a piece of work spans a long period of time. A two-second chat turn does not; an hour-long approval does. Take the human approval out of the product and the right answer becomes "just write the loop", with no workflow engine anywhere.

Decision 2 · talk to the model directly, with no gateway in between

Every message this agent sends to the model begins with the same large block of text: the instructions and the list of available tools. That block might be a few thousand words, and it is identical on every message of every conversation.

Anthropic's API lets you mark that block and say, in effect, "this is the same as last time, do not charge me full price to read it again". This is called prompt caching, and for an agent handling thousands of conversations a day it is the largest cost saving available.

A model gateway is a middle layer — LiteLLM is the common one — that makes switching model providers easy later. The catch is that it speaks a common request format modelled on OpenAI's, and that format has no field for marking a cacheable block. Putting a gateway in the middle therefore means giving up the discount.

Two smaller things also come from talking directly: an exact token-counting call, which turns the project's character-based context budget into a real token budget, and a batch mode at half price for running the offline evaluation suite.

What decides it is the large unchanging prefix. A support agent with a short prompt that differed on every request would lose nothing to a gateway, and portability would then be worth more than the saving.

Decisions 3 and 4 · where the model and the code run

Use Anthropic's own API, unless the shop already buys everything through AWS — in which case take Bedrock. You get new features some weeks later, but you get one bill and one identity system, and for most companies that trade is worth making. The application code barely changes either way.

Run the agent in containers, wherever the shop already runs its software. A support agent lives inside an existing estate and does not get to have opinions about the deployment target. It inherits them.

What the design deliberately refuses

Four things it will not use

  • An agent framework. The hand-written loop contains three safety controls — a limit on how many steps the agent may take, a check for whether it is going round in circles, and a spending ceiling. All three need to see the whole conversation so far to work at all. Handing the loop to a framework means handing over the only place in the code that can see the full trajectory, to save writing 350 lines once.
  • A vector database. This agent does not search documents. Its rules are in a file and its orders are in Postgres. Adding one would mean operating a component with no job.
  • A guardrails product as the main control. Those tools scan for rude language and personal data, which is worth having at the edges. They cannot catch the failure that actually matters here — the agent saying "your order was delivered" when it was not. That needs a comparison against the real order record.
  • A fully managed agent platform. The approval gate and the ownership check are what make this agent trustworthy. Renting a loop you cannot inspect gives away exactly those two things.

The identity decision, which the source document says people usually get wrong

The shop already has customers logging in, through whatever system it uses. The agent verifies whatever token that system issues and adds nothing. Introducing a second identity system just for the agent would look like diligence and would actually be a mistake.

But there is one check no login system provides: is this particular customer allowed to act on this particular order? A login proves who somebody is. It does not stop the agent fetching a different customer's order record when the model asks for one.

That check is roughly fifteen lines at the tool boundary, driven by a declaration in the agent's world file. It is the one identity-related thing this agent genuinely has to build.

Why so much of the design says "ours"

Read the layer-by-layer table in that repo and a striking number of rows say the component is built in-house: context assembly, the control loop, the input and output contracts, the policy checks, the determinism mechanism, the cost accounting. For an ordinary production agent that would be a cost you were trying to reduce. For this agent it is the point.

The AI Harness Catalog states what an agent must contain. If a framework hides the context assembly, the control loop and the failure handling, the reference agent cannot demonstrate that those parts exist — which is the single job a reference agent has. It is the same inversion as the learning build in section 05: here, building it yourself is the deliverable rather than the overhead.

One honest inconsistency, already recorded. The document describes the stack you would build for a real shop. The repository itself runs on Groq, using an OpenAI-shaped client, because the exercise runs hundreds of times a day and has to stay free — which means it currently gives up the prompt caching that justified skipping the gateway. The project did not paper over this. It recorded the trade-off, priced it, and noted what would make it worth revisiting. Holding a recommended stack and a running stack apart, with the difference written down, is more honest than pretending a constrained choice was the ideal one.

Where this disagrees with the rest of this page

The gateway. ADR-0002 says put a model gateway in on day one, always. This agent says no gateway, and the argument holds: the gateway's real cost is losing provider-specific capability, and a large unchanging prompt prefix is exactly where that cost peaks. The ADR now carries the exception, stated precisely — skip the gateway when the prefix is large, stable and high-volume; keep it when the prompt is short or varies per request.

The billing-support case. Case 1 in section 05 recommends the OpenAI Agents SDK with a gateway — same industry, different answer. It reached that answer because it assumed no long human wait and no large fixed prompt. Change those two facts, as this agent does, and the right stack changes with them. That is the method working, not a contradiction: the shape questions produce the answer, and two agents in the same industry can legitimately need different stacks.

What changes when you bring a cloud

If you build any of these agents on AWS, Azure, Google Cloud or Databricks instead of your own machines, most of the stack does not change at all. The harness stays the same. Your tools stay the same. Everything you were going to build yourself, you still build yourself. Three things change, and only three.

1

Where the model comes from

Every cloud resells the models through its own service, and you use theirs.

2

The plumbing underneath

Database, queue, object storage, secrets — you use the managed versions instead of running your own.

3

Identity and permissions

This is the one that genuinely improves, and it is worth more than the other two put together.

What never changes, on any cloud

The harness. LangGraph, the Claude Agent SDK, the OpenAI Agents SDK and a hand-written loop are all just Python packages. They run in a container, and a container runs anywhere. No cloud makes any of them a better or worse choice.

Your tool contracts. A tool exposed over MCP works the same everywhere, because MCP is a protocol rather than a service.

Everything on your build list. The run contract, the context policy, the permission model, the evaluation cases, the budget governor, the human interface. These encode your business, and no cloud has an opinion about your business.

And the important one: no cloud sells you context management. Deciding what stays in the model's context window as a long run grows is the most expensive concern in this whole page, and buying a cloud does nothing for it whatsoever. If your agent's hard problem is context, the cloud decision is close to irrelevant to you.

What always changes: the model and the plumbing

Each cloud resells the major models through its own service — Bedrock on AWS, Azure AI Foundry, Vertex AI on Google, Model Serving on Databricks. You get new model features weeks or months later than going direct, because each cloud has to integrate them. In exchange you get one bill, one identity system, and data that never leaves your cloud account — frequently the reason the decision was made, and a perfectly good one.

What that means for the gateway decision: if you are committed to one cloud and one provider, the cloud's model service is your gateway, and adding LiteLLM in front buys little. If you want more than one provider, or budgets and caching in one place, keep the gateway and point it at the cloud service.

The plumbing swap — Postgres becomes RDS or Cloud SQL, Redis becomes SQS or Pub/Sub, MinIO becomes S3 or Blob Storage — changes no design decision at all. It changes who gets paged when the database runs out of disk.

What changes for the better: identity

This is the part worth reading carefully, because it addresses the one concern every framework on this page scores badly on. Throughout, agent identity has been the unsolved problem: the agent holds one powerful service account, so every user of the agent inherits every permission that account has, and one bug or one injection reaches all of it.

A cloud solves a large part of this, because clouds have spent fifteen years on exactly this problem. Two mechanisms matter.

Workload identity means the agent stops holding secrets. Instead of an API key in an environment variable, the running container gets an identity from the platform itself, and that is what services check. AWS calls it an IAM role for the task, Azure a managed identity, Google workload identity. There is no key to leak, rotate or accidentally commit. Outside a cloud you would reach for SPIFFE and SPIRE to get this, which is a real project; here it is configuration.

Delegated user identity means the agent acts as the person who asked. The agent carries that user's own credentials down to the data, and the platform enforces what they may see. On Databricks this is Unity Catalog applying grants, row filters and column masks to the query itself. If your agent serves many users with different permissions, this is the strongest single argument for building on a cloud at all.

The pattern: a cloud helps with the Trust band and the substrate, and does nothing for the Context band. Identity, policy, durability and operations are exactly what a cloud sells, and it sells them well. Context assembly and context lifecycle are exactly what it does not sell — and those are the heaviest-weighted concerns on this page.

So the honest summary is this. If your agent's difficulty is permissions, long waits, or governed data, a cloud removes a large amount of genuine work. If your agent's difficulty is managing what the model knows, a cloud changes your invoice and very little else.
