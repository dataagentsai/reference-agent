Support Agent Escalation Flow

Escalation is one of four routes out of a user turn, and one of the three that never reach the model. It is decided by regex, before intent, in a pure function that runs outside the loop.

Refuse Out of scope. Typed refusal, no model call.
Escalate A human takes over. Typed escalation, no model call.
Direct One deterministic handler, one tool call, no model call.
Agentic The loop. The only path that reaches the model.

01What escalation costs

An escalation is resolved in a single regex scan. No model call, no tool call, no approval record — one checkpoint write and a typed result. The router's own docstring makes the claim, and the entrypoint test holds it to it with a scripted LLM client that has nothing in it, so reaching the model would raise.

That is the deterministic-first thesis made structural rather than aspirational: "get me a human" resolves at stage S2, free and binary, and cannot be talked out of it by a model that would like to try helping first.

02The path a turn takes

Escalation branches at exactly one point — router._decide — and rejoins the common tail immediately. Everything before the branch is shared with the other three routes; everything after it is the same recording and checkpointing every route does.

03What triggers it

Two rules, both on router.Rules, both versioned configuration rather than code — AAC-0101 gates a routing change the way it gates a model change. The reason string attached to each pattern is carried all the way through to the typed result and the span.

PatternReason carried forwardTurn that fires it
\b(human|agent|manager|supervisor|real person)\b the customer asked for a human “just put me through to a human”
\blost in transit\b the item is reported lost in transit “the courier says it is lost in transit”

The second rule is the interesting one: nobody asked for a human. It is a policy escalation — a case class the agent is not permitted to resolve alone — expressed in the same mechanism as the request for one. Both are matched case-insensitively, and both are checked against the raw turn text before any intent classification runs.

04Why order matters

The three predicate groups in _decide run in a fixed sequence: refuse, then escalate, then intent. This is not stylistic. A turn that also names a workable intent must still escalate, because a customer asking for a person should not be routed into a loop that tries to help first.

05The two typed shapes

Escalation crosses two contract boundaries and changes type at each. Escalate is the router's decision; Escalated is what the caller gets back. Neither is a string, and the round-trip through the discriminated union is asserted rather than assumed.

# contracts/results.py — what the router decides
class Escalate(_Frozen):
    """A human takes over. Triggered by P-ESCALATE, or asked for outright."""
    kind: Literal["escalate"] = "escalate"
    reason: str

# contracts/results.py — what the entrypoint returns
class Escalated(_Frozen):
    kind: Literal["escalated"] = "escalated"
    reply: str
    reason: str
    ticket_id: str | None = None

# entrypoint/__init__.py — the dispatch that converts one into the other
case Escalate():
    result = Escalated(
        reply="Let me pass you to a colleague who can help with that.",
        reason=decision.reason,
    )

The reply is a fixed string, deliberately. It is the same sentence whichever rule fired, so the reason — the thing an operator needs — travels in a field rather than in prose an evaluation would have to parse. AHC-0010 is the constraint: this is the surface an evaluation drives, so every variant must be assertable without reading English.

06What it emits, and what the edge does with it

The route decision is recorded on the agent.route span, where all three attributes are required by the telemetry contract — a span missing any of them fails conformance rather than quietly producing a trace nobody can group.

AttributeValue on an escalation
agent.route.kind"escalate"
agent.route.reasonthe matched rule's reason string
agent.router.rules_version"v1"
agent.result (on http.chat)"escalated"

Over HTTP an escalation is a 200, alongside Completed and Refused. The agent worked correctly and the answer is "a person will take this" — returning 4xx would make every dashboard count correct behaviour as an error rate. The body carries the fixed reply and "outcome": "escalated"; the reason stays on the span, not in the response.

08Where the flow stops short

The route is complete as a classification and incomplete as a handoff. These are the seams, in rough order of how much they would cost a real deployment.

no side effect

Nothing is handed to anyone

No queue write, no ticket, no notification. The customer is told "Let me pass you to a colleague" — which is a promise no tool has confirmed, and the system prompt three modules away says never promise what a tool has not confirmed. The reply is the only artifact of the escalation.

contracts/results.py:110

ticket_id is declared and never set

The field exists on Escalated and is written nowhere in src, tests, or evals. It reads as the intended attachment point for the missing handoff — a slot cut for a part that was never fitted.

not sticky

The next turn routes normally

_record appends the reply and nothing else; only pending_approval_id survives a turn. So the message after an escalation is classified from scratch, and the agent will happily answer it while a colleague is nominally taking over.

router rule 1

agent and manager are broad words

The pattern matches the noun anywhere in the turn. "the delivery agent left it at the wrong door" escalates — a routine damaged/missing-item turn the agent is built to handle. Tightening it means anchoring on the request, not the noun.

domain.py:25

Intent.ESCALATE is unreachable

The enum member exists, but escalation is decided before intent classification runs, so the router can never produce it. Vestigial from an intent-first design.

contracts/results.py

The only variant with no termination

Completed, NeedsApproval, Refused and Failed each carry a TerminationReason. Escalated does not, and the enum has no member for it — so a dashboard grouping turns by termination reason silently drops escalations.

R-011 · F-010

The loop cannot escalate

Escalation exists only ahead of the loop. A trajectory that has failed twice has no way to say "hand this to a person" — the grid cell for control-loop escalation is empty, which is the finding R-011 raised against model routing and which applies unchanged here.

agenttwin/omission.py

A missed escalation leaves no evidence

World diff, truth and bounds all report success on a turn that should have escalated and didn't: nothing changed, nothing false was said, no budget was exceeded. This is the failure class the omission oracle and required_when exist for, and the escalation rules are not yet expressed there.
