The Escalation Rebuild

Escalation today is a regex, a string, and nothing else. This is the design for making it a durable, measurable, three-tier decision with a human on the other end — and the argument for building it on a table rather than a broker.

01Queue or no queue

You asked this directly, so it goes first. The answer turns on separating two things the word "queue" usually welds together:

  • A durable record of outstanding work — what must not be lost.
  • A transport that pushes it to a consumer — how someone finds out.

A Postgres table gives you the first outright. It gives you the second too, via LISTEN/NOTIFY. A broker is only strictly required when you need the second across service boundaries, to many independent consumers, with backpressure you don't control.

Broker — Kafka / SQS / Rabbit

What you gain

  • Fanout. CRM, paging, analytics and the agent desk all consume without the writer knowing they exist.
  • Backpressure and DLQ as infrastructure rather than as code you maintain.
  • Consumer groups. Twenty desks pulling work without a SELECT … FOR UPDATE SKIP LOCKED you wrote yourself.
  • Cross-service reach when escalation leaves this process for a system you don't own.
Broker — the cost

What it breaks

  • Two sources of truth. Writing the row and publishing the message is not atomic — the dual-write problem. Fixing it properly means a transactional outbox, which is more machinery, not less.
  • A second place duplicates enter. At-least-once delivery is the same class of bug as AAC-0076, which you already paid for once in trigger.
  • It contradicts the codebase's own rule. "One write, because two writes can disagree" — InMemoryCheckpointStore. "The conversation id goes in the same row rather than a second table, so the two can never disagree and no transaction is needed" — PostgresCheckpointStore.
  • Another system in the P6 durability story to run, secure and reason about.
Recommendation

Start with queue-as-table in Postgres plus LISTEN/NOTIFY. One row is the truth, written in the same transaction as the checkpoint. Notification is a side effect of the commit, so the two cannot disagree.

Run the arithmetic before buying a broker: at 1M conversations/day and a 5% escalation rate you are at ~0.6 escalations/second. Postgres does not notice that. Brokers earn their place at fanout and cross-service reach, not at this volume.

Add a broker when — and only when — a consumer you don't own needs the event. At that point add it as a transactional outbox reading this same table, so the table stays the source of truth and the broker becomes a projection of it. That is a later, additive change, not a rewrite.

02Does the catalog cover this?

You asked whether AHC and AAC cover over- and under-escalation. I checked all 49 A6-tagged obligations in evals/a6_obligations.json (catalog v0.12.0).

Finding

Not one A6 obligation mentions escalation, handoff, deferral, or human oversight of a decision. The single obligation tagged oversight in A6 is AAC-0094, "only approved models are reachable" — model governance, not human oversight.

Five relevant obligations do exist — all tagged to other archetypes. The file's own elsewhere_note sanctions claiming them: "A test claiming one of these is not making a mistake — it is evidence that the obligation applies to this archetype and is not tagged for it."

ObligationTaggedTitleWhat it governs here
AAC-0020A1Over-refusal rate on in-scope inputsthe exact shape of over-escalation
AAC-0088A10Guardrail false-positive and false-negative ratesthe FP/FN frame both directions need
AAC-0043A4Escalation to a human works under loadthe path holds at concurrency
AAC-0062A7Handoff payloads are completewhat the human actually receives
AAC-0087A10Confidence scores are calibratedprerequisite for the model-driven tier
AAC-0042A4Conversation-level cost and turns to resolutionthe frustration proxy

Under-escalation has no obligation in any archetype. The closest is AAC-0088's false-negative half, written for guardrails rather than handoff. That gap is worth filing upstream — and you found it independently already: the omission oracle in agenttwin/omission.py exists because "a clinical triage agent's worst failure is a missed escalation, and every oracle we own reports success on it."

Practically: claim AAC-0020, AAC-0043, AAC-0062, AAC-0087 and AAC-0088 with @pytest.mark.discharges, and express under-escalation as required_when declarations the omission oracle can see — the mechanism is already built and currently has no escalation rules in it.

03When to escalate — three tiers

Your instinct is right that this is a business rule set, configurable and versioned. The structural principle that keeps it auditable: the model proposes, a deterministic rule disposes. A model score is an input to a threshold, never the decision itself — otherwise no escalation is reproducible from its trace, and AAC-0059 and AAC-0100 both fail.

Tier 1 · deterministic · pre-model · exists today

Explicit request and hard policy classes

The customer asks for a person; the case class is one the agent may not resolve alone. Regex or classifier over the raw turn, checked before intent, costing nothing. Keep exactly as is — but tighten rule 1, which currently fires on "the delivery agent left it at the wrong door." Anchor on the request (talk to|speak to|get me|put me through + person-noun), not the noun alone.

Tier 2 · deterministic · over state, not text · missing

Rules the conversation earns

This is the tier that answers "escalation without the customer asking." All computable, all testable, none needing a model:

  • same intent unresolved across N turns
  • N consecutive tool failures, or a Failed result on a money path
  • loop terminated on STEP_BUDGET_EXHAUSTED, COST_CEILING_REACHED or OSCILLATION_DETECTED
  • order value or refund amount over a threshold
  • customer tier, or a prior escalation within 24h
  • an approval that has sat undecided past its window

Evaluated at the end of each loop iteration as well as per turn — which closes the R-011 / L2×P4 gap where a failing trajectory currently has no way to say "hand this to a person."

Tier 3 · model signal · thresholded deterministically · missing

Frustration and novelty

A cheap classifier emits {frustration: 0.0–1.0, novelty: 0.0–1.0} per turn. It does not escalate. A Tier-2-style rule compares it to a configured threshold and escalates. The score, the model id, the threshold and the rule id all go on the span, so any decision replays exactly.

Gate this tier on AAC-0087: an uncalibrated score thresholded at 0.7 is a number with no meaning. Ship Tiers 1 and 2 first; Tier 3 needs labelled data that only running the first two produces.

Rules live beside router.Rules as versioned configuration, so AAC-0101 already gates changing them the way it gates a model change. Give the rule set its own version and put it on every span.

04Over- and under-escalation

These are a confusion matrix, and you cannot tune one without measuring the other. Both need a ground truth that only the human on the far end can supply — which is why outcome capture is part of the data model, not a later analytics concern. Without it, neither rate is computable and every threshold is a guess.

EscalatedNot escalated
Human was needed correct handoff under-escalation — customer stranded; leaves no evidence
Agent could resolve over-escalation — human time burnt, queue swamped, slower for the customer correct autonomy

How each becomes visible

  • Over-escalation — the resolving human marks the outcome agent_could_have. Directly countable, and cheap: the person closing the ticket is the label. Mirrors AAC-0020's over-refusal rate.
  • Under-escalation — leaves no trace by construction. Three complementary detectors:
    1. required_when declarations in the world, read by the existing omission oracle — the offline half.
    2. A customer who re-opens, or escalates on turn N+3 having been refused at N — countable from the conversation store.
    3. Sampled human review of non-escalated conversations, per AAC-0014's continuous-scoring shape.

Set the target asymmetrically and say so out loud. For support, an under-escalation costs a stranded customer while an over-escalation costs a few minutes of agent time — so bias toward escalating and cap the over-rate by budget rather than driving it to zero. Write the chosen numbers into the config; a threshold nobody wrote down is a threshold nobody can review.

05The data model

One new table, in agent_state — the schema that is never simulated, because this is oracle data. Written in the same transaction as the checkpoint that records the turn.

CREATE TABLE agent_state.escalations (
    id              text PRIMARY KEY,          -- the customer-facing ticket handle
    conversation_id text NOT NULL,
    run_id          text NOT NULL,             -- the turn that raised it
    customer_id     text NOT NULL,

    -- why, and reproducibly
    tier            smallint NOT NULL,         -- 1 | 2 | 3
    rule_id         text NOT NULL,             -- which rule, not just which tier
    rules_version   text NOT NULL,             -- AAC-0101
    reason          text NOT NULL,
    signal          jsonb,                     -- tier 3: score, model id, threshold

    -- AAC-0062: what the human receives, captured at raise time
    handoff         jsonb NOT NULL,            -- transcript ref, order ids, what was tried

    -- lifecycle
    state           text NOT NULL,             -- queued|assigned|in_progress|resolved|abandoned|expired
    priority        smallint NOT NULL DEFAULT 5,
    created_at      timestamptz NOT NULL DEFAULT now(),
    assigned_to     text,
    assigned_at     timestamptz,
    resolved_at     timestamptz,
    expires_at      timestamptz NOT NULL,      -- borrowed from approvals

    -- the ground truth that makes FP/FN computable at all
    outcome         text,                     -- resolved|agent_could_have|misrouted|customer_gone
    outcome_by      text,
    outcome_note    text
);

-- the desk's read: oldest waiting work, highest priority first
CREATE INDEX escalations_queue ON agent_state.escalations (state, priority DESC, created_at)
    WHERE state IN ('queued', 'assigned');

-- the customer's read, and the resume check on the next turn
CREATE INDEX escalations_conversation ON agent_state.escalations (conversation_id, created_at DESC);

And one field on the conversation, mirroring what approvals already do:

class Conversation(BaseModel):
    ...
    pending_approval_id: str | None = None
    pending_escalation_id: str | None = None   # the "not sticky" fix

That single field is what stops the agent silently answering the next message as though no handoff happened. _turn checks it exactly where it already checks pending_approval_id.

Claiming work is SELECT … FOR UPDATE SKIP LOCKED — the standard queue-as-table claim, and the same shape as InMemoryDeliveryLog.claim, which already taught you that a claim needs an expiry because a settling finally does not survive SIGKILL.

06When no human is available

This is where the current design fails hardest, and the fix is a rule the codebase already states: never promise what a tool has not confirmed. Today the agent says "Let me pass you to a colleague" with nothing behind it. The rebuilt path must check capacity before it speaks.

SituationWhat the agent saysWhat it does
Desk open, wait under SLA"Connecting you now — about 4 minutes."queue, real estimate from queue depth ÷ throughput
Desk open, long queue"About 25 minutes. I can stay on this, or call you back."queue, offer callback, keep serving other topics
Desk closed"The team is back at 09:00. I've logged this as #E-4417."queue with a real handle, promise a time you can keep
Nobody claims it before expires_atproactive: "Still waiting — I haven't forgotten."raise priority, page the on-call, never silently drop
Customer leaves—state abandoned, outcome customer_gone — a countable failure, not a disappearance

The distinction that matters: a queued escalation is 202, not 200 — accepted, not finished — matching what NeedsApproval already returns. The status code is the difference between "we did it" and "we owe you."

Frustration

Handle it as a Tier 2 input first, not a Tier 3 one. Repeated same intent, turns-to-resolution over the AAC-0042 budget, a second refusal in one conversation — these are countable and need no classifier. Add sentiment scoring only once those are in place, because a model that escalates on tone alone is the fastest route to an over-escalation problem you cannot explain.

07Tracing it for analysis

The join key is escalation_id, and it must appear on the raising span, the desk's claim, and the resolution — otherwise queue wait and handle time are not computable from the trace.

SpanAttributesAnswers
agent.escalation.raiseescalation.id, .tier, .rule_id, .rules_version, .signal.score, .signal.threshold, .prioritywhy this fired, and would it fire again
agent.escalation.queue.depth_at_raise, .estimate_s, .desk_openwas the promise we made keepable
agent.escalation.claim.assigned_to, .wait_squeue wait distribution, by rule
agent.escalation.resolve.outcome, .handle_sthe FP/FN numerators

Add each to telemetry.CONTRACT with the required set, so a span missing rule_id fails conformance rather than quietly producing analytics nobody can slice. Sliced by rule_id, the resolve span answers the question that actually tunes the system: which rule produces escalations humans say the agent could have handled?

08Build order

Each step is shippable and leaves the system better than it found it. Nothing here needs a broker.

#StepCloses
1escalations table + pending_escalation_id; raise writes a row and fills ticket_id; 202 not 200the dead field, "not sticky", the false promise
2_turn short-circuits on a pending escalation, with a truthful holding replythe agent answering over a live handoff
3Tighten Tier 1 rule 1 to request-anchored patterns"the delivery agent left it at the wrong door"
4Reviewer surface: GET /escalations, POST /escalations/{id}/claim, /resolve with outcome capture"we built the queue and never built the actor"
5Tier 2 rules, evaluated per turn and per loop iterationimplicit escalation; R-011 / L2×P4
6Capacity check + real wait estimates + expiry sweeperpromising a colleague who isn't there
7Spans, contract entries, FP/FN dashboards by rule_idAAC-0020, AAC-0088
8required_when escalation rules for the omission oracleunder-escalation, offline
9SSE push to the browser; LISTEN/NOTIFY to the desk"does the user keep asking?"
10Tier 3 signal, gated on calibrationAAC-0087 — last, deliberately
The one thing to decide before coding

Steps 1–9 need no broker and no new infrastructure. Step 4 is the pivot: who is the human? An internal desk you build (this design), or an existing system — Zendesk, Intercom, a Slack channel? If it's an external system, the escalations table becomes an outbox projecting into it, and that is the one place a broker starts to earn its keep.
