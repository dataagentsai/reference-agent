Question 01

What are the different kinds and shapes of AI application?

AI applications come in ten shapes. The industry you're in, which model you use and how big it is don't set the shape. Two questions do:

  1. Who owns control flow? Your code, or the model?
  2. What does the output touch? A person reading it, code consuming it, or the real world?

The shape matters because it decides what the harness around the model has to do. Each shape adds a new way to fail, so each one needs more from the harness.

#ShapeWhat it isControl flowExamples
A1Single-Turn Transform One call in, one answer out. No tools, no retrieval, no memory. The model reworks the text it was given. Your codeClassify, summarise, translate, rewrite
A2Structured Extractor Output is a typed object read by downstream code, not by a person. A schema turns quality failures into type failures. Your codeEntity extraction, form filling, function arguments
A3Grounded Answerer Search a set of documents, then write an answer from what came back. The search step and the writing step fail independently, so each is tested on its own. Your codeRAG, document Q&A, knowledge assistant
A4Conversational Assistant Multi-turn and stateful. Keeps context, memory and user history across turns, but takes no action on its own. Your codeSupport chat, tutoring, guided intake
A5Deterministic Workflow A fixed graph of steps with an LLM call at each node. The handoffs between steps are where new failures appear. Your codeChains, pipelines, batch enrichment
A6Tool-Using Agent The model picks which tools to call, in what order, and when to stop. This is the biggest jump in what you have to test. The modelReAct loops, function-calling agents
A7Multi-Agent System Several agents hand work to each other, under a supervisor or by passing it along. On top of A6, it adds failures in who is allowed to do what, how much each may spend, and how far one agent's mistake can spread. Several modelsSupervisor/worker, specialist handoff
A8Artifact Producer Output is code, SQL, config or a document that will be run or shipped. You can check it by running it, which is the strongest check any shape gets. EitherCode generation, text-to-SQL, infrastructure-as-code
A9Autonomous Operator Runs unattended on a trigger or schedule, with real side effects and nobody watching live. The model, unattendedScheduled agents, auto-remediation, background workers
A10Classifier · Router · Judge The model's output steers other machinery: a routing decision, a guardrail verdict, a quality score. You won't see its errors unless you evaluate the evaluator. Your codeLLM-as-judge, safety classifiers, model routers

Shapes are tags, not a tree

A real system usually has more than one shape. A support agent like the one in this repo is a Conversational Assistant (A4), a Tool-Using Agent (A6) and a Grounded Answerer (A3) all at once. It may also use a Router (A10) to decide when to hand off to a human. Give a system every shape that applies and build the harness for all of them.

Why this matters for the harness

Every shape needs a common core from the harness: input handling, output checks, tracing, cost limits, evaluation. Beyond that core, each shape adds what is new about it. The line that matters most runs between A5 and A6. Up to A5, your code decides what happens next. From A6 on, the model decides, so the harness has to supply the limits your code used to enforce: which tools are allowed, step and cost budgets, stop conditions, and approval before irreversible actions.

In the AI Harness Catalog (AHC), a single-turn transform (A1) needs about 50 harness capabilities, while a multi-agent system (A7) needs about 75. The more control the model has, the more the harness has to do.

Question 02

What layers make up a whole AI application?

A request travels left to right: from the person, through your application and your harness, optionally through an AI gateway, to the model provider that runs the model. The answer comes back the same way. Underneath, a lab trained the model and a cloud runs every box. Each box is a role. One company can fill several roles, which is where most of the confusion comes from.

LayerWhat it doesExamplesYou…
1 · ApplicationWhere a person, or a trigger, starts the work and sees the result.Chat UI, IDE, Slack bot, API, schedulerBuild
2 · Orchestration & contextDecides the steps, assembles what the model sees, retrieves documents, keeps memory, and calls tools.Claude Agent SDK, LangGraph, LlamaIndex, plain code, MCP servers, pgvectorBuild
3 · AI gateway (optional)A proxy in front of the providers. It gives all your apps one API and enforces keys, budgets, rate limits, routing and fallback. It runs no model itself.LiteLLM Proxy, Portkey, Kong AI Gateway, Azure APIM, Databricks AI GatewayRun, or buy as a service

Four pairs people confuse

PairThe difference
Gateway vs providerA gateway forwards requests. A provider runs the model. LiteLLM or Portkey on its own can't answer a single prompt; it needs a provider behind it. If you remove the gateway, your harness calls the provider directly. That's fine for one app and one provider. Add a gateway when several apps, teams or providers need one set of keys, budgets and logs.
Provider vs labA lab trains the model. A provider serves it. Anthropic is both: the lab that trains Claude and the provider behind the Anthropic API. AWS trains no Claude model, yet Bedrock serves Claude. Meta trains Llama but serves it to almost nobody; you get Llama from Bedrock, Databricks or your own vLLM.
Provider vs cloudAWS the cloud rents you machines (EC2, GPUs). AWS Bedrock is a model provider that happens to run on that cloud. Same company, different layers. Choosing AWS as your cloud doesn't force Bedrock. Your app on AWS can still call the Anthropic API.
Model vs providerOne model, many front doors. The same Claude model is served by the Anthropic API, Bedrock, Vertex and Azure AI Foundry. Features, prices and release timing can differ slightly between them. The model is what thinks; the provider is where you call it.

So when someone says "we use Anthropic", ask which role they mean. It could be the model (Claude), the provider (the Anthropic API) or the framework (the Agent SDK). Each is a separate choice.

How one request flows

  1. A person, or a trigger, sends a request through the application.
  2. The harness (orchestration & context) builds the prompt. It pulls relevant documents through RAG, recalls memory, and lists the tools the model may use.
  3. If there is a gateway, it checks the key and budget, logs the call, and picks a provider.
  4. The provider runs the model, which either answers or asks for a tool. If it asks for a tool, the harness runs the tool, feeds the result back, and loops to step 3.
  5. The answer passes back through output guardrails to the person. Tracing and cost records are written along the way.

Where the harness sits

The model is one box on the far right, and you rent it. Most of the engineering, and every failure from Question 01, lives in the outlined parts: orchestration & context and the cross-cutting band. That is the agent harness, everything around the model that makes it safe and dependable to run. The gateway is drawn dashed because it's optional. When you have one, it enforces some of the harness's controls, such as budgets and key management, at a single shared point.

Question 03

What does an agent harness have to take care of?

The harness is everything that is neither the model nor your business logic: the ordinary, predictable code that turns a model into a system. The AI Harness Catalog (AHC) splits it into 16 areas. Each one owns a single question, such as "what is the model told?" or "when does the system stop?"

Most teams build two of them, observability and evals, and call the harness done. The other fourteen are where agents fail in production.

Five groups make the sixteen easier to remember:

#Area · the question it ownsWhat it coversWhat breaks without it
What goes in and out of the model
L1Context assembly
What is the model told?		 Prompt templates and versions, where retrieved text goes, ordering, compaction, token budget, fencing untrusted content.AHC-0011 · Untrusted content is fenced and labelled at assembly Text inside a support ticket is read as an instruction. The budget silently truncates the evidence the answer needed.

Parameters change when the SDK default changes.

Not every shape needs all sixteen

Thirteen areas apply to every shape from Question 01. Three appear only as the model gains control:

  • Tool layer (L3): tool-using agents, multi-agent systems and autonomous operators (A6, A7, A9), plus the sandbox for artifact producers (A8).
  • Control loop (L4): from deterministic workflows (A5) upward. A single-turn transform has no loop to stop.
  • Human-in-the-loop (L14): approvals for agents that act (A6, A7, A9), escalation for assistants (A4), rejection for artifact producers (A8).

State & memory (L5) is a similar case. Every shape owes one core rule about how state is saved, and the rest arrive with conversations (A4) and agents.

Where the areas sit in the Question 02 diagram

  • Orchestration & context box: context assembly, tools, control loop, state & memory, I/O contracts, human-in-the-loop.
  • AI gateway, if you have one: it can carry part of model invocation, concurrency, cost accounting and failure handling (fallback) for every app at once.
  • Cross-cutting band: policy enforcement, identity, observability, evals, determinism, release & configuration.
In AHC, layers and concerns are different things. The 16 above are layers: which part of the harness a rule belongs to. Concerns are a separate tag for which quality a rule serves: the nine ISO/IEC 25010 qualities (reliability, security, safety, maintainability…) plus cost. The catalog holds about 110 rules, and each has one layer and one concern.

Question 04

What does the support reference agent look like, end to end?

The reference agent does customer support for a clothing store. In Question 01's terms it is a tool-using agent (A6). It uses no agent framework, because a framework would own the control loop, context assembly and failure handling, which are the layers this tutorial is about. Instead it has one module per harness area from Question 03, and an import contract that fails the build if a module reaches across the architecture.

Mapped to the roles in Question 02

RoleIn the reference agent
ApplicationChatwoot (chat widget and human desk), the login portal, and a built-in /chat page
Harnesssupport_agent: edge, router, loop, context, policy, tools, approvals, escalation, state, identity, telemetry, cost and the rest, one module per area
AI gatewayLiteLLM proxy. It holds the provider credential and gives the agent its own key with a budget, rate limit and model allowlist.
Model providerGroq, through its OpenAI-compatible API
Modelgpt-oss-120b. A config value, checked against the endpoint at startup.
ToolsThe order system's MCP server (src/order_system) in front of a real Saleor store
CloudLocal Docker Compose: Postgres, LiteLLM, Keycloak, Saleor, plus Langfuse, Temporal and Chatwoot behind profiles

Follow one message

  1. Log in and chat. The customer logs in through the portal (Keycloak) and types in the Chatwoot widget. No token ever reaches the browser; the login is kept server-side.
  2. Edge. Chatwoot's webhook arrives. The agent checks the HMAC signature and a timestamp no more than five minutes old, confirms the contact is verified, resumes that customer's stored login, and takes the delivery id so a resent message can't act twice.
  3. Router. On every turn, a deterministic router decides whether the model is needed at all. Direct answers what the spec can answer. Refuse handles requests like "give me a discount". Escalate handles "get me a human". All three cost nothing and never enter the loop. Only Agentic goes on.
  4. Model call. The loop assembles context, with untrusted text fenced and old history trimmed rather than summarised, and runs the pre-model policy check. The llm module, the only one allowed to import a provider SDK, calls the LiteLLM proxy, which forwards to Groq. The reply is parsed into a typed result and checked by post-model policy.
  5. Tool call. If the model asks for a tool, pre-tool policy runs, then the MCP client calls the order system with the customer's exchanged token and an idempotency key. The server verifies the token and, for a refund, the approval, and only then calls Saleor. The result is capped at 8,000 characters, fenced, and fed back to the model.
  6. Stop. The loop ends when the model is done, or when the harness stops it at 12 steps, $0.50, or the same step repeating three times. The reason is always recorded.
  7. Wait for a person when needed. A refund over ₹10,000 returns NeedsApproval. The turn saves a checkpoint, a Temporal workflow waits for up to 24 hours, and a reviewer decides at the desk. An escalation hands the chat to a person in Chatwoot with the facts attached as a private note.
  8. Reply. The answer goes back through Chatwoot. The trace, redacted before export, goes to Langfuse with the task's cost.

The six tools

ToolKindScope needed
get_order, list_ordersReadThe customer's own orders only, filtered by the verified token
cancel_order, change_addressWriteorders:write

The architecture is enforced, not just documented. Import contracts in pyproject.toml fail the build if any module except llm imports a provider SDK, any module except tools speaks MCP, or the agent imports the order system or its own simulator. The order system checks the agent's authority independently, so the agent can't learn to satisfy the rules instead of being held to them.

Question 05

End-to-end function stack

What actually runs when a customer sends one message? Each scenario below follows one real turn through the reference agent: every function in order, with its file and line, what it receives and returns, and everything that leaves the process. That covers what goes to the model, over MCP, to Saleor, to Postgres, to Temporal and to OpenTelemetry.

How these were captured. Each scenario is one real turn through the full composed stack:
  • Keycloak-shaped JWT at the edge
  • the real router and loop
  • the model through the LiteLLM proxy to Groq (openai/gpt-oss-120b)
  • the order system's MCP server over the real Saleor store
  • Postgres for the checkpoint, and Temporal for the delivery claim
Every function entry and return in src/ was recorded with Python's sys.monitoring, and the wire payloads were tapped where they leave the process. Nothing is reconstructed. The script is agent-harness-tutorial/capture/capture_turn.py; run it again to get a fresh trace.

What to notice

  • One tool, two model calls. The first call picks the tool; the second writes the answer from its result. The second is about 5× larger because the whole order list goes back in.
  • Identity never comes from the model or the body. It is verified at the edge. A new token addressed to the order system travels in MCP _meta, and the order system verifies it again before it touches Saleor.
  • The tool surface depends on the customer. issue_refund is on the server but hidden from this customer, who lacks refunds:write. The model is offered request_refund, a local tool that routes through approvals.
  • Policy ran at five points: pre-model twice, pre-tool, post-tool, post-model, and the final reply screen. The post-model check took the longest (about 30 ms), because it confirms every order id in the reply appears in the tool result.
  • Reads skip the ledger. An idempotency key was minted (run…:0:1) but not sent, because list_orders is a read.
  • Postgres was written once: a single checkpoint row at the end. Nothing was written during the loop.
  • Cached tokens are billed as full input. Groq reported 256 cached prompt tokens on call 1, but _from_wire doesn't read prompt_tokens_details.cached_tokens, so the meter prices them at the full input rate. The cost is slightly overstated, never understated.
